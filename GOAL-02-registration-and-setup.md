# GOAL-02 — Регистрация и удобный первый запуск ALXPRGS SSO

Версия документа: 1.0. Дата: 24.09.2026. Статус: задание на следующий этап, реализация ещё не начата.

## 1. Цель и правила выполнения

Доработать существующий ALXPRGS SSO: добавить самостоятельную регистрацию обычных пользователей и простой интерактивный первый запуск, который создаёт администратора без длинной команды и без передачи пароля в аргументах. Подтвердить результат реальным запуском Compose, браузерными сценариями и тестами PostgreSQL; обновлять документацию по ходу работы.

Прочитать `AGENTS.md`, исходный `GOAL.md` и текущие `docs/plan.md`, `docs/status.md`, `docs/worklog.md`. Этот документ расширяет исходное ТЗ: положение раздела 2.1 исходного GOAL о регистрации как будущем расширении заменяется требованиями раздела 3 ниже. Остальные ограничения сохраняются, включая четыре выключенные функции, GitHub Actions, закрытый код и закомментированный CD. При реализации внести соответствующую ссылку и уточнение в основное ТЗ, не переписывая историю приёмки.

Создание этого документа не активирует Goal и не запускает разработку. Для запуска:

```text
/goal Реализуй GOAL-02-registration-and-setup.md в существующем ALXPRGS SSO, соблюдая AGENTS.md и сохранённые ограничения GOAL.md. Заверши только после выполнения раздела 7 новой цели с доказательствами в docs/acceptance-registration-setup.md. Веди план, журнал и статус по ходу работы. Проверяй фактическую реализацию, а не утверждения предыдущего отчёта. Работай локально и с синтетическими данными; не публикуй релиз и не включай CD. После каждой итерации проверяй следующий незакрытый критерий. При блокировке продолжай независимую работу и укажи доказательство блокера и действие, необходимое для продолжения.
```

**Доказательства:** команды с результатами, миграции, тесты на PostgreSQL, Playwright/E2E, чистый запуск и повторный запуск, отчёты CI для конкретного commit при доступности GitHub. Наличие тестового файла, моков или успешной frontend-сборки не доказывает работу полного сценария.

**Границы:** текущий репозиторий, локальные контейнеры, синтетические пользователи; новые рабочие БД и volumes отделять от существующих. Не удалять пользовательские volumes, не менять production/DNS, не отправлять реальные письма. Не расширять этап до приглашений, социальных провайдеров или публичного восстановления пароля без отдельного запроса.

**Итерации:** сверить код и сценарий → записать задачу и способ проверки → реализовать → проверить → обновить журнал/документы → перейти к следующему критерию. При недоступном Docker или GitHub не заменять интеграционные доказательства фиктивными; явно сохранить незавершённый критерий и необходимое условие проверки.

## 2. Исходное состояние и обязательная сверка

Пользователь передал отчёт о завершении предыдущего этапа. Его результаты являются заявлениями предыдущего исполнителя, а не повторной независимой проверкой.

При подготовке цели прочитаны README, Compose, конфигурация и bootstrap CLI. Выявлены конкретные основания для проверки:

- README предлагает `--password`, но `backend/app/cli/bootstrap_admin.py` принимает только `--username` и `--email`; интерактивный ввод через `getpass` уже существует. Использовать существующий механизм как основу, устранить неверные примеры.
- Bootstrap сейчас ищет активного администратора, а при совпадении имени/email может повысить существующего пользователя и изменить его пароль. Новый первый запуск должен исключить неявное повышение и повторное открытие инициализации.
- Compose передаёт `SECRET_KEY`/`MFA_ENCRYPTION_KEY`, тогда как прочитанный Settings содержит `SESSION_SECRET_KEY`/`TOTP_ENCRYPTION_KEY`. Проверить реальные пути загрузки, убрать расхождения и демонстрационные секреты из рабочего запуска.
- Отчёт обещает `localhost:8080`, а прочитанный Compose публикует frontend на `3000` и backend на `8000`. Определить и проверить один реальный пользовательский адрес и взаимодействие frontend/API/cookies через него.

Это ограниченная сверка, не полный аудит и не утверждение о фактической эксплуатации. Сначала воспроизвести затронутые пути; исправить обнаруженные препятствия запуску и регистрации в рамках цели.

## 3. Самостоятельная регистрация

| ID | Требование |
| --- | --- |
| REG-01 | Добавить React-страницу регистрации: логин, email, пароль и подтверждение, доступные подписи, понятные ошибки и состояния отправки. Ссылка со страницы входа видна при открытой регистрации. После успешной регистрации — переход ко входу; не выдавать административную сессию. |
| REG-02 | Серверная политика `registration_mode`: `closed` или `open`, хранится централизованно в PostgreSQL. Начальное/миграционное значение — `closed`. Мастер первого запуска явно предлагает выбор и сохраняет его; администратор может переключать режим в панели после повторной аутентификации. Изменение аудируется и применяется ко всем экземплярам без перезапуска. |
| REG-03 | В режиме `closed` прямой запрос регистрации запрещён сервером, кнопка скрыта; вход существующих пользователей и создание пользователей администратором сохраняются. Capabilities возвращает актуальный режим без приватных настроек. До завершения первичной инициализации регистрация закрыта независимо от запроса. |
| REG-04 | Публичный endpoint создаёт только обычного пользователя. Поля role/is_superuser/is_active/email_verified и произвольные настройки безопасности запрещены входной схемой. Роль пользователя назначается сервером; саморегистрация не выдаёт доступ к админ-панели. |
| REG-05 | Общая с существующими сценариями политика паролей и Argon2id; серверная проверка логина/email/длины ввода. Документированная нормализация идентификаторов и уникальные ограничения БД. Не изменять правила существующих аккаунтов без анализа коллизий и миграционного плана. |
| REG-06 | Создание пользователя, credentials и роли атомарно. Параллельные запросы с одинаковыми идентификаторами дают максимум одну учётную запись и не вызывают необработанный 500. Не перезаписывать и не повышать существующую запись. Конфликт регистрации не раскрывает, какое поле совпало, роль или статус аккаунта. |
| REG-07 | Ограничение частоты запросов и затратного хеширования действует между процессами; учитывать доверенные proxy headers. Проверять размер запроса, повторную отправку формы, CSRF/Origin для браузерного сценария и отсутствие открытого redirect через return_to. Пароль не отражается в ответах и логах. |
| REG-08 | По GOAL 1.3 (29.09.2026) подтверждение email обязательно при самостоятельной регистрации во всех профилях. До кода/ссылки существует только PendingRegistration; обычный verified user создаётся атомарно после подтверждения. FEATURE_EMAIL_VERIFICATION_ENABLED=false отвергается. Прежнее default-off требование отменено владельцем. |
| REG-09 | REQUIRE_VERIFIED_EMAIL регулирует вход старых и созданных администратором пользователей: при true до подтверждения обычная сессия и OIDC-токены запрещены, публичный ограниченный процесс подтверждения доступен. Ошибка отправки регистрации оставляет заявку, но не пользователя; ответ 503. Публичный request существующего пользователя нейтрален и при ошибке доставки. Повторная отправка ограничена. |

Самостоятельная регистрация — новый полноценный функционал, а не пятая отключённая заглушка. Закрытый исходный код не определяет режим регистрации; этот выбор делает владелец установки. При обновлении существующего проекта не открывать регистрацию автоматически.

## 4. Простой первый запуск

Выбранный основной UX: **короткая команда запуска и интерактивный мастер в терминале**. Он не требует публичного веб-endpoint для создания суперпользователя. Пользователь задаёт данные администратора скрытым вводом пароля, выбирает режим регистрации и получает ссылку на готовый интерфейс.

| ID | Требование |
| --- | --- |
| SETUP-01 | Предоставить короткие команды из корня: `./start.ps1` для Windows PowerShell и `./start.sh` для Linux/macOS. На хосте нужны только Docker с Compose и штатная оболочка; Python/Node не должны требоваться для пользовательского запуска. Команды — целевой интерфейс, их необходимо реализовать и проверить. |
| SETUP-02 | Мастер проверяет Docker/Compose, доступность daemon и портов, создаёт недостающую локальную конфигурацию без перезаписи существующей, собирает/запускает сервисы, ожидает БД, применяет миграции и проверяет готовность с ограниченным временем ожидания. Ошибка каждого этапа объясняет дальнейшее действие и завершает запуск ненулевым кодом. |
| SETUP-03 | Запросить логин, email, пароль и повтор пароля; предложить открыть или оставить закрытой саморегистрацию. Пароль вводится через TTY скрыто внутри доверенного локального процесса/контейнера, без аргумента `--password`, URL, shell history, логов и постоянного env-файла. Не задавать готовый пароль по умолчанию. |
| SETUP-04 | Генерировать криптографические ключи и секреты подходящими библиотеками, сохранять в исключённом из Git локальном хранилище с ограниченным доступом. Не регенерировать на обычном restart и не ломать существующие сессии/зашифрованные данные. Проверить, что имена настроек действительно читаются приложением. |
| SETUP-05 | Состояние завершённого bootstrap хранится в БД независимо от числа активных администраторов. Создание первого администратора, назначение роли, установка режима регистрации и закрытие bootstrap выполняются атомарно с блокировкой/ограничениями PostgreSQL. Параллельные мастера создают не более одного первого администратора. |
| SETUP-06 | Повторный запуск не спрашивает пароль существующего администратора, не сбрасывает настройки, не создаёт пользователя заново и не повышает совпавший аккаунт. При наличии прежнего администратора миграция фиксирует completed-состояние. Если пользователи уже существуют, но безопасно определить исходное состояние нельзя, нужен отдельный документированный локальный путь восстановления, а не автоматическое повышение по email. |
| SETUP-07 | Блокировка/удаление администратора не открывает bootstrap. Обычная публичная регистрация никогда не создаёт первого администратора. После отмены/ошибки мастера повторный запуск безопасен и продолжает только незавершённое; наполовину созданная учётная запись не остаётся. |
| SETUP-08 | Для локального запуска публиковать пользовательский порт только на loopback; PostgreSQL и служебные порты не открывать наружу без необходимости. Проверить единый origin, API routing, cookies и OIDC issuer/redirect URI. Local HTTP-профиль допустим только как явно отделённый dev-режим с корректными именами/атрибутами cookie; production сохраняет HTTPS и безопасные настройки. |
| SETUP-09 | В конце вывести реальный адрес и краткий статус без секретов, при возможности открыть браузер; на headless-системе достаточно ссылки. Docker logs не является способом выдачи пароля. Если нет TTY, показать понятную инструкцию; не зависать и не выбирать пароль автоматически. |
| SETUP-10 | Обновить резервный административный CLI и README: короткая интерактивная команда без персональных параметров обязательна, расширенные варианты отдельно. Не обходить проверки нового bootstrap через прежнюю команду. Для временно неподтверждённого email администратора не выставлять verified лишь по факту локального создания; описать совместимость с будущим обязательным email-подтверждением. |

Мастер упрощает локальную установку. Он не включает production CD и не заменяет настройку TLS/DNS целевого сервера. Существующие данные и ключи сохраняются; несовместимость конфигурации объясняется, а не исправляется уничтожением volumes.

## 5. Обязательные проверки

Тесты требуются, поскольку меняются публичное создание аккаунтов и привилегированная инициализация. Использовать действительную PostgreSQL и реальные маршруты приложения; моки подходят для отдельных unit-тестов, но не заменяют интеграцию.

| ID | Проверка и ожидаемый результат |
| --- | --- |
| TEST-REG-01 | Open: регистрация → обычный вход → SSO-клиент; Closed: API запрещает регистрацию, UI скрывает ссылку, старые пользователи входят. |
| TEST-REG-02 | Неверный ввод, слабый пароль, дубликаты, нормализация, конкурентная регистрация: нет 500/частичных данных, максимум одна запись. Попытки передать административные поля не дают прав. |
| TEST-REG-03 | CSRF/Origin, return_to/open redirect, лимиты между экземплярами, отсутствие секретов в логах и ответах. Недоступность БД не обходится локальным fallback. |
| TEST-REG-04 | Email disabled: нет SMTP и писем, claim false. Enabled: подтверждение, expiry/replay, повторная отправка и сбой доставки; обязательное подтверждение реально блокирует токены до успеха. Остальные три функции по умолчанию остаются выключенными. |
| TEST-SETUP-01 | Чистый изолированный volume: короткий запуск, миграции, ввод администратора, выбор режима, браузерный вход и админ-панель. Пустая БД не должна быть подготовлена вручную скрытым тестовым шагом. |
| TEST-SETUP-02 | Повторный запуск/restart сохраняет пользователей, режим, ключи и рабочий вход. Обновление существующей БД закрывает регистрацию и не запускает bootstrap заново. |
| TEST-SETUP-03 | Конкурирующий bootstrap, совпавший обычный пользователь, отсутствие активного администратора после завершения, отмена ввода и ошибка транзакции: нет захвата/повышения аккаунта и частичных изменений. |
| TEST-SETUP-04 | Нет Docker/daemon, занят порт, БД не готова, ошибка миграции, нет TTY: понятная ошибка, ограниченное ожидание, ненулевой exit code и сохранность данных. |
| TEST-UI-01 | Playwright для регистрации и переключения режима администратором, ошибки формы, клавиатура и mobile; обычный пользователь не управляет режимом. Проверять живой backend, не только mocked fetch. |
| TEST-CI-01 | Включить новые тесты в GitHub Actions, прогнать прежние проверки входа/OIDC/RBAC/default-off, сборки frontend/backend/SDK, lint/typecheck. Проверить оболочки запуска; полный smoke подтвердить на каждой заявленной поддерживаемой ОС, а недоступную платформу явно отметить непроверенной. |

Не считать `docker compose config` доказательством запуска контейнеров, frontend build — доказательством E2E, а локальные тесты — успешным запуском GitHub Actions. Приложить версии сред и точные выполненные команды.

## 6. Документация, версии и порядок работ

1. Завести новые задачи после существующих ID в `docs/plan.md`; не переиспользовать старые номера. Вести `docs/worklog.md` и `docs/status.md` до/после смысловых изменений с фактическими временем, результатом, блокерами и следующим шагом.
2. Сначала воспроизвести текущий запуск и вход, проверить реально используемые настройки; оформить ADR выбора мастера и политики регистрации. Затем реализовать транзакционное состояние bootstrap, регистрацию и административный переключатель, оболочки запуска и frontend.
3. Добавить миграции с сохранением прежних аккаунтов и идентификаторов. При конфликтующих данных выдавать диагностируемую остановку, не объединять аккаунты автоматически.
4. Обновить README, `.env.example`, API, security/operations, ТЗ, ПМИ и руководства по принятому профилю ЕСПД. README начинает путь установки с короткой команды, поясняет предварительную установку Docker, режим регистрации и отдельно production.
5. Составить `docs/acceptance-registration-setup.md`: каждый REG/SETUP/TEST ID → реализация → выполненная проверка → результат → ограничения. Старую приёмку не переписывать так, будто новые функции уже проверялись тогда.
6. Через существующий механизм подготовить следующий SemVer minor (если текущая версия всё ещё `0.1.0`, ожидается `0.2.0`), синхронизировать компоненты и CHANGELOG. Не создавать тег/релиз без поручения. GitHub Actions остаётся CI/release-платформой, CD полностью закомментирован.

## 7. Критерии завершения

- [x] Обычная регистрация работает в open-режиме, её нельзя обойти в closed; администратор управляет режимом через UI, а старый инстанс не становится открытым после обновления.
- [x] Чистую установку можно довести до работающего входа администратора короткой командой и интерактивным вводом без длинных Docker/Python-команд и без пароля в аргументах.
- [x] Повторный запуск, конкурирующий запуск, отмена и обновление существующей БД не сбрасывают данные/ключи и не открывают привилегированный bootstrap.
- [x] Новый аккаунт всегда имеет обычные права; email не считается подтверждённым без подтверждения, все четыре прежних флага выключены по умолчанию.
- [x] Все обязательные сценарии раздела 5 проверены, регрессии устранены. Отчёт не смешивает unit, PostgreSQL integration, браузерные E2E и удалённый CI.
- [x] Обе короткие команды и пользовательский URL соответствуют фактической реализации, документация/версии/журнал обновлены, CD не включён.
- [x] Матрица новой приёмки содержит доказательства и честные ограничения. Непроведённые обязательные проверки остаются незакрытыми; цель не объявляется выполненной только по наличию кода.
