Сохранить полезные изменения GOAL-03; не начинать проект или полный аудит с нуля. Для каждого исправления нужны воспроизведение и проверяемый результат, а не только изменение статуса в отчёте.

Прочитать `AGENTS.md`, GOAL-01 (`GOAL.md`), GOAL-02, GOAL-03, текущие plan/status/worklog и реестр дефектов. Сопоставить этот документ с фактическим кодом: некоторые замечания могли быть уже исправлены. Старое «PASSED» не заменяет проверку, но подтверждённые результаты не нужно повторять без причины.

Не повторяй весь предыдущий этап без необходимости. Исправляй продукт вместе с regression tests, сохраняй пользовательские изменения и веди документацию по ходу работы. CI и release остаются в GitHub Actions; CD остаётся отключённым. Заверши только по разделу 7 с доказательствами, честно отделив локальную готовность от результата GitHub Actions. ## 2. Ограничения и порядок

- Сохранить Python/FastAPI/PostgreSQL/React, SDK, четыре default-off флага, closed registration при обновлении и закрытый код. Не включать CD, не публиковать релиз, не менять production/DNS.
- Рабочее дерево содержит много предыдущих изменений: не выполнять reset/clean и не терять их. Фиксировать фактическую ревизию и наличие незакоммиченных файлов при проверках.
- Первыми выполнить G4-DB и его отрицательные тесты. До защиты fixtures не запускать полный integration-набор с унаследованным `DATABASE_URL`.
- Затем последовательно: email → Passkey → межпроцессные лимиты → CI и точечная итоговая регрессия. Приоритет безопасности выше косметических замечаний.
- Использовать только синтетические данные и изолированные ресурсы. Не очищать существующие volumes/БД; локальные SMTP и тестовые браузерные аутентификаторы вместо настоящих получателей и credentials.
- После каждого шага: обновить план → воспроизвести → исправить → выполнить тест → записать доказательства/следующий шаг. Не расходовать время на повторение уже подтверждённых независимых проверок.
- Недостаток лимитов не делает цель выполненной. Сохранять точку продолжения, незакрытые критерии и фактические результаты. Не скрывать блокеры за mocks/skip/ослаблением требований.

## 3. Адресные задачи

### G4-DB — Защита данных при тестах

Основание: в прочитанном `tests/conftest.py` общий `DATABASE_URL` используется для подключения, затем fixture выполняет `TRUNCATE … CASCADE`.

- Выделить `TEST_DATABASE_URL` без fallback на рабочий `DATABASE_URL`; отсутствие явно заданной тестовой среды — понятный отказ до разрушительных SQL.
- Создавать отдельную БД/схему для запуска с проверяемой принадлежностью этому запуску, отдельным ограниченным DB-пользователем и явной процедурой очистки. Одного наличия подстроки `test` в имени недостаточно.
- Проверять целевую БД и маркер владения перед очисткой. Не выдавать тестовому пользователю права на рабочие базы. Не показывать пароль из DSN в ошибках.
- Отрицательные тесты: переменная отсутствует; передан рабочий/непринадлежащий запуску адрес; маркер неверен; только общий `DATABASE_URL`; неподходящие права. Отказ должен происходить до `TRUNCATE/DROP`; на отдельной контрольной БД убедиться, что данные не изменены.
- Положительный тест: свой изолированный контур создаётся, мигрируется, тестируется и очищается, не затрагивая соседний.

### G4-EMAIL — Реальный путь подтверждения почты

Основание: в `test_features_pg.py` обязательность email временно выключается, чтобы войти и запросить подтверждение. Это не доказывает работоспособность сценария неподтверждённого пользователя.

- В enabled-профиле с `REQUIRE_VERIFIED_EMAIL=true` регистрация → запрос/получение письма → подтверждение → обычный вход должны работать без изменения политики и административного вмешательства.
- До подтверждения нельзя выдавать обычную сессию и OIDC-токены. Использовать ограниченный безопасный процесс подтверждения; он не даёт доступ к профилю или админке, не раскрывает аккаунты и имеет rate limits/TTL.
- Проверить локальную SMTP-доставку, просроченный/повторный токен, повторную отправку, сбой доставки, неправильного пользователя и отсутствие повышения прав. Убрать обход политики из приёмочного теста.
- Default-off по-прежнему не требует SMTP, ничего не отправляет и не выставляет `email_verified=true`.

### G4-PASSKEY — Полный WebAuthn-сценарий

Основание: просмотренный новый integration-набор не содержит полноценного enabled lifecycle Passkey с виртуальным аутентификатором.

- В живом браузере с виртуальным WebAuthn authenticator проверить регистрацию Passkey, повторный вход, несколько credentials и удаление; последний удалённый credential больше не работает.
- Проверить неверные/повторные/просроченные challenge, RP ID/origin, user verification и принадлежность credential пользователю. Не подменять `verify_*` успешным mock-ответом в сквозном тесте.
- При недостающем UI/API реализовать недостающие части согласно исходному ТЗ. Сохранить поведение синхронизируемых passkeys и default-off.
- Сохранить browser report и безопасные traces; конфигурация trace должна действительно давать артефакт при ошибке, даже если retries=0.

### G4-LIMITS — Межпроцессные лимиты и доверенные proxy

Основание: тест с названием distributed выполняет последовательные запросы одного ASGI-приложения; прочитанный `get_client_ip` принимает `X-Forwarded-For` без проверки источника.

- Запустить минимум два независимых backend-процесса с общей PostgreSQL. Чередовать и одновременно отправлять запросы через оба, проверить общий предел и гонки счётчика; один глобальный Python-объект не является двумя процессами.
- Изменение клиентом forwarding-заголовков не должно позволять обходить лимит. Определить доверенные proxy и проверить реальную цепочку gateway/backend; непроверенным источникам не доверять заголовки.
- Проверить неуспешные попытки, TTL окна и поведение при отказе БД. Никакого fail-open и необоснованных штрафов всем пользователям из-за ошибки адресации.

### G4-CI — Диагностика падений и воспроизводимость

Подтверждённый baseline после отправки текущих изменений: [CI run 36027756634](https://github.com/alxprgstech/sso/actions/runs/36027756634), commit `2c1de5b668482d2bc11707fe565e3d1ab8711f4c`. Backend job падает на сборе `tests/test_python_sdk.py`: `ModuleNotFoundError: No module named 'alxprgs_sso'`. В backend job устанавливается backend, но общий набор включает SDK-тесты: исправить разделение наборов или установку требуемого SDK. SDK isolated job, frontend, version consistency и CD-template check прошли. Логи PostgreSQL также содержат `role "root" does not exist`: проверить пользователя healthcheck отдельно; не подменять этим подтверждённую причину падения pytest. После исправления collection повторить CI: последующие ошибки пока могли быть скрыты ранним отказом.

- Найти доступные логи первого и последнего неуспешного GitHub Actions run, указать URL и commit SHA. Если доступа нет, честно отметить это и локально воспроизвести команды из workflow. Не угадывать историческую причину по текущему YAML.
- Убедиться, что workflows устанавливают все необходимые зависимости и применяют миграции к пустой тестовой БД до integration. Проверить, что тесты действительно используют `TEST_DATABASE_URL`.
- Подготовить воспроизводимые unit/integration/E2E jobs, оба профиля, выделенные синтетические аккаунты и автоматическую подготовку данных; не зависеть от вручную созданного `compose_admin` и его фиксированного пароля.
- SDK проверять из wheel в отдельном каталоге, без серверного conftest и затенения пакета исходниками. Проверить зависимости сборок, Python/Node версии, lock-файлы и соответствие выполняемых команд путям.
- Добавить E2E сборку/старт сервисов, ожидание готовности, миграции, браузер и очистку только ресурсов конкретного run. Артефакты падений сохраняются; таймауты ограничены.
- Проверить release-кандидат на привязку к точному SHA и успешным обязательным проверкам без фактической публикации. Сохранять минимальные permissions и закреплённые SHA Actions.
- Исправлять действующие `.github/workflows/ci.yml` и `release.yml`. Владелец уточнил: просьба означала commit/push, а не комментирование или отключение Actions. CI не отключать ради зелёного статуса; release не публиковать, CD не активировать.
- Локально прогнать эквивалентные команды на чистой тестовой среде и проверить YAML/Actions syntax. Это доказывает локальную готовность, но не успех удалённого GitHub run. После разрешённого push проверить CI именно отправленного SHA; недоступность обязательного удалённого прогона остаётся явно указанным блокером.

## 4. GitHub и проверенная ревизия

Сопоставить предыдущие упавшие runs с актуальным кодом. После отправки исправлений отслеживать новый run по commit SHA. Старый красный статус не доказывает ошибку текущей версии, а локальная проверка не доказывает успех CI. Если новая публикация изменений не разрешена в текущей задаче, подготовить изменения и явно указать необходимый push; не публиковать релиз вместо запуска CI.
