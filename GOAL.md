Версия: 1.2. Дата: 24.09.2026. Статус: задание на реализацию.

## 1. Контракт цели

Создать в этом репозитории пригодную к развёртыванию закрытую систему единого входа для инфраструктуры `alxprgs.tech`: сервер идентификации на Python/FastAPI с PostgreSQL, React-интерфейс пользователя и администратора, устанавливаемую Python-библиотеку интеграции и русскоязычную документацию в Markdown. Реализовать TOTP, Passkey, Recovery codes и подтверждение почты полностью, включая миграции, API, интерфейс и тесты, но оставить **все четыре возможности отключёнными по умолчанию**. Доказать готовность воспроизводимыми проверками, двумя демонстрационными клиентами и матрицей соответствия требованиям.

Это файл постановки цели, а не свидетельство готовности продукта. Его создание само по себе не запускает реализацию и не активирует persistent Goal в Codex.

### 1.1. Запуск в Codex

В среде с поддержкой Goals передать следующую команду; содержимое файла должно быть прочитано агентом:

```text

Все четыре отложенные возможности должны работать в тестовом профиле и оставаться недоступными в конфигурации по умолчанию. Работай в этом репозитории и изолированных локальных тестовых средах. После каждой итерации выбирай следующий незакрытый критерий с учётом рисков безопасности; при внешнем блокере продолжай независимую работу и сообщи доказательства блокировки и минимальное необходимое действие владельца. Не объявляй цель выполненной при пропущенных обязательных проверках.

### 1.2. Проверка, ограничения и границы

- Проверяемые результаты: исходники, миграции, сборки, тесты, отчёт CI, два OIDC-клиента, инструкция запуска, пакет SDK и документы из раздела 5.
- Неизменяемые ограничения: Python, FastAPI, PostgreSQL, React; закрытый исходный код; четыре отложенные возможности выключены; отсутствие собственных криптографических алгоритмов.
- Разрешённая область: репозиторий, синтетические данные, локальные контейнеры, публичная официальная документация и зависимости после проверки лицензий.

## 2. Введение, основания и назначение

Наименование: ALXPRGS SSO. Основание: пользовательское ТЗ и уточнение от 24.09.2026 об отключении всех четырёх дополнительных возможностей. Номер договора, заказчик как юридическое лицо, утверждающие подписи и сроки не заданы; не выдумывать их.

Система централизует аутентификацию пользователей и подключение будущих сервисов домена. Допускается использование в научных работах с синтетическими данными и воспроизводимыми экспериментами. Это не разрешение на открытое распространение исходников или пользовательских данных.

### 2.1. Принятые проектные допущения

1. Предлагаемый production issuer и адрес кабинета: `https://auth.alxprgs.tech`; админ-панель: `/admin` на том же origin. Адрес согласовать до production, не менять issuer незаметно после выпуска токенов.
2. Первая версия обслуживает одну организацию. Мультитенантность, SAML, LDAP, социальные провайдеры и SCIM не входят в обязательный объём.
3. Основной доступ в конфигурации по умолчанию — логин и пароль. Саморегистрация закрыта; пользователей создаёт администратор. Приглашения и публичная регистрация — отдельное расширение.
4. Письма не отправляются при выключенном подтверждении почты. Обычный парольный вход не зависит от наличия SMTP. Восстановление доступа при потере пароля выполняется документированной административной процедурой с принудительной сменой временного пароля и отзывом сессий; публичный email reset не входит в первую версию.
5. Python SDK включён в целевой результат как запрошенное преимущество. Название пакета предварительное: `alxprgs-sso`; публикация в публичный PyPI не требуется.
6. Точные версии runtime и библиотек выбрать при реализации из поддерживаемых совместимых версий, закрепить в lock-файлах и ADR. Не считать версии из памяти актуальными.

| ARCH-04 | Состояние одноразовых операций, лимиты и отзыв сессий работают между несколькими процессами. In-memory хранилище допустимо только в изолированных тестах. Redis добавлять только с обоснованием; PostgreSQL остаётся обязательным. |

### 3.2. Единый вход и управление пользователями

| ID | Требование |
| --- | --- |
| SSO-01 | Реализовать согласованный профиль OpenID Connect: Discovery, JWKS, Authorization Code с PKCE S256, token и UserInfo endpoints. Использовать проверенную протокольную библиотеку; FastAPI OAuth2 helpers сами по себе не являются OIDC-провайдером. |
| SSO-02 | Поддержать confidential web clients и публичные клиенты без встроенного client secret. Исключить Implicit и Resource Owner Password Credentials. Redirect URI — точное совпадение с зарегистрированным значением, без wildcard. |
| SSO-03 | Authorization code одноразовый, короткоживущий и привязан к клиенту, redirect URI и PKCE. Проверять issuer, audience, подпись, сроки, nonce и state там, где они применимы. Не принимать ID token как access token. |
| SSO-04 | Scopes как минимум `openid`, `profile`, `email`; выдавать только разрешённые клиенту claims. `sub` — стабильный непрозрачный идентификатор, не email. Неподтверждённый email не превращать в `email_verified=true`. |
| SSO-05 | Короткоживущие access tokens, ротация refresh tokens, выявление повторного использования с отзывом семейства. Закрепить TTL в конфигурации и документации. Предлагаемые стартовые значения: code 60 с, access token 5 мин, idle session 12 ч, absolute session/refresh 7 дней. |
| SSO-06 | Асимметричная подпись, JWKS с `kid`, документированная ротация ключей с периодом перекрытия. Приватные ключи вне репозитория и логов. |
| SSO-07 | Локальный logout, отзыв выбранной/всех SSO-сессий, revocation endpoint, RP-initiated logout с проверкой возвратного адреса. Описать, что выход из SSO сам по себе не удаляет локальные сессии всех клиентов. |
| SSO-08 | Заблокированный пользователь не может входить, обновлять токены или использовать серверную сессию. Для автономно проверяемого JWT допустимое окно до истечения access token ≤ 5 мин; админ-операции проверяют текущий статус немедленно. |
| USR-01 | Создание, блокировка и редактирование пользователя; смена пароля с проверкой текущего доступа; управление собственными сессиями. Не допускать повышения роли через self-service API. |
| USR-02 | Идемпотентная административная команда создания первого администратора, без пароля по умолчанию; секрет не попадает в аргументы команд, историю и логи. |
| USR-03 | Серверный RBAC: пользователь и администратор как минимум. Не допускать случайного удаления/блокировки последнего активного администратора. |

### 3.3. Реализованные, но отключённые возможности

Ключевое уточнение владельца: **TOTP, Passkey, Recovery codes и подтверждение почты отключены по умолчанию одновременно**. Наличие кода не означает доступность функций.

| Флаг сервера | Значение по умолчанию | Реализация при включении в тестовой среде |
| --- | --- | --- |
| `FEATURE_TOTP_ENABLED` | `false` | Подключение с подтверждением первого кода; второй фактор; удаление после повторной аутентификации; защита от повторного использования временного шага. Секрет шифруется отдельным управляемым ключом. |
| `FEATURE_PASSKEY_ENABLED` | `false` | Регистрация, вход и удаление нескольких WebAuthn credentials; короткоживущие одноразовые challenges, проверка origin/RP ID и user verification. Парольный вход продолжает работать. |
| `FEATURE_RECOVERY_CODES_ENABLED` | `false` | Выпуск и замена набора резервных кодов, показ только при выпуске, хранение хешей, атомарное одноразовое погашение. Recovery code заменяет второй фактор после пароля, но не является самостоятельным первым фактором. |
| `FEATURE_EMAIL_VERIFICATION_ENABLED` | `false` | Запрос/повторная отправка подтверждения, шаблоны письма, SMTP-адаптер, одноразовый ограниченный по времени токен, подтверждение адреса, инвалидирование при смене email. |

Обязательные правила:

- `SEC-FLAG-01`: сервер является единственным источником состояния функций; frontend получает безопасный список capabilities. Нельзя включить функцию через localStorage, запрос пользователя или только переменную frontend.
- `SEC-FLAG-02`: при `false` скрыты UI-элементы, закрыты enrollment/verification/login/recovery endpoints соответствующей функции (единый документированный ответ, например 404 `feature_disabled`), отсутствуют фоновые отправки и другие побочные эффекты. Проверять прямые HTTP-запросы, а не только интерфейс.
- `SEC-FLAG-03`: тестовый профиль включает функции без изменения default-конфигурации. Проверить каждую отдельно и допустимые сочетания. Recovery codes разрешать только при включённом TOTP и подключённом TOTP у пользователя; недопустимые настройки отклонять явно.
- `SEC-FLAG-04`: отключение фактора у ранее подключённых пользователей не должно незаметно понижать обязательный уровень защиты. При несовместимой MFA-политике вход закрывается с документированным путём восстановления администратором. Никакого скрытого bypass.
- `SEC-FLAG-05`: подтверждение email и обязательность подтверждённого адреса — разные настройки. `REQUIRE_VERIFIED_EMAIL=false` по умолчанию; значение `true` при отключённой функции подтверждения — ошибка конфигурации. Неподтверждённый адрес не использовать для чувствительных решений.
- `SEC-FLAG-06`: Passkey проверяется для `auth.alxprgs.tech` как предлагаемого RP ID и точного HTTPS origin; не расширять доверие автоматически на все поддомены. Dev localhost настраивается отдельно. Обработать особенности синхронизируемых passkeys, а не требовать безусловного роста sign counter для всех устройств.
- `SEC-FLAG-07`: письма тестировать с локальным почтовым приёмником. Не отправлять реальные письма для доказательства работоспособности.

### 3.4. Интерфейс

- `UI-01`: русский интерфейс, адаптация для телефона и desktop; подписи полей, управление клавиатурой, видимый фокус, доступные ошибки и состояния загрузки. Не раскрывать наличие аккаунта текстом ошибки входа.
- `UI-02`: вход, выход, профиль, смена пароля, сессии; интерфейсы всех отложенных возможностей в enabled-профиле.
- `UI-03`: админ-панель: пользователи, роли, клиенты OIDC, redirect URI, отзыв сессий, журнал аудита с пагинацией и фильтрами. Секрет клиента показывается только при создании/ротации. RBAC проверяется API, а не только React.
- `UI-04`: перед изменением пароля, факторов, ключей клиента и критических прав — недавняя повторная аутентификация; при включённых факторах учитывать политику MFA. Опасные действия подтверждаются пользователем интерфейса.

### 3.5. Python SDK

- `SDK-01`: отдельный устанавливаемый пакет с `pyproject.toml`, типами, версией, wheel/sdist и тестами; не зависит от внутренних модулей SSO-сервера.
- `SDK-02`: удобная FastAPI dependency проверки bearer access token и прав. Настройка через issuer/audience и окружение, пример подключения в 3–5 строк без учёта импортов и объявления самого приложения.
- `SDK-03`: web-login helper для Authorization Code + PKCE: start/callback/logout, state/nonce, серверное хранение сессии. Отличать проверку API-токена от полноценного браузерного входа.
- `SDK-04`: разрешённые алгоритмы и точная проверка issuer/audience/exp/nbf; ограниченный по времени JWKS cache, обновление при неизвестном `kid`, ограничение частоты обновлений; таймауты сети и типизированные ошибки. URL провайдера задаёт приложение, не недоверенный токен.
- `SDK-05`: настройки TLS и проверки подписи нельзя ослаблять по умолчанию. Роли и scopes проверяются явно; отсутствие требуемого claim означает отказ.
- `SDK-06`: два небольших отдельных FastAPI-клиента с различными client IDs демонстрируют вход в один сервис и переход во второй без повторного ввода пароля через SSO-сессию. Отдельно показать 401, 403, logout и окно действия ранее выпущенного JWT.

## 4. Надёжность, безопасность и эксплуатация

1. Пароли: Argon2id через поддерживаемую библиотеку, индивидуальная соль, параметры с измеренным временем проверки, ограничение длины ввода без молчаливого усечения; процедура rehash.
2. Session cookies: `Secure`, `HttpOnly`, подходящий `SameSite`, host-only; не раздавать общую cookie на `.alxprgs.tech`. CSRF-защита изменяющих состояние cookie-auth запросов; точные CORS allowlists; HTTPS в production.
3. Распределённые ограничения попыток входа, проверки кодов, отправки писем и создания challenges; защита от перебора без бессрочной блокировки жертвы. Доверенные proxy headers задаются явно.
4. Операции погашения codes/tokens и ротации refresh tokens атомарны. Гонки проверять на реальном PostgreSQL, а не только на моках.
5. Аудит входов, ошибок, смены пароля/факторов, блокировок, прав, клиента и отзыва сессий. Не логировать пароли, токены, cookies, TOTP secrets, recovery codes, приватные ключи или полные письма. Политика хранения и удаления персональных данных документируется.
6. Структурированные логи с correlation ID, health/readiness, метрики без секретов. При недоступности БД операции аутентификации завершаются отказом, а readiness отражает сбой.
7. Docker Compose для воспроизводимого локального запуска; production-инструкция с reverse proxy/TLS, секретами, миграциями, ротацией ключей, backup/restore и откатом. Сохранность данных не зависит от эфемерного контейнера.
8. Тест восстановления БД из backup на отдельном экземпляре. Ключи шифрования и подписи резервируются отдельно; восстановление TOTP проверяется в enabled-профиле.
9. Модель угроз охватывает захват аккаунта, session fixation, CSRF/XSS, open redirect, token replay, IDOR, эскалацию прав, компрометацию соседнего поддомена и утечки секретов. Угрозы связать с тестами.
10. CI обязательно выполняется в GitHub Actions: lint, typecheck, unit/integration/E2E, сборки, проверка зависимостей и секретов. Нет известных непринятых critical/high уязвимостей в поставляемых компонентах; исключение требует решения владельца с обоснованием и сроком.
11. Производительность измерить на описанном стенде: конфигурация, объём синтетических данных, конкурентность, длительность, p50/p95, throughput и ошибки. Числовой production SLA, RPO/RTO и ожидаемую нагрузку владелец пока не задавал; не выдумывать гарантии.

| VER-03 | Предоставить одну документированную команду подготовки `patch`, `minor`, `major` или prerelease: синхронизация версий, проверка метаданных, обновление `CHANGELOG.md`. | CI-01 | `.github/workflows/ci.yml`: проверки на pull request и push в основную ветку; ручной запуск для диагностики. Покрыть backend, frontend, SDK, PostgreSQL integration, E2E обоих профилей функций, миграции, безопасность и сборки. Документировать обязательные checks для защиты основной ветки. |
| CI-02 | Фиксированные зависимости, сторонние Actions закреплены полным commit SHA, минимальные permissions, таймауты, управление конкурентными запусками и ограниченный срок хранения отчётов. PR-проверки работают без production secrets; не выполнять недоверенный PR-код с привилегированным токеном через `pull_request_target`. |
| REL-01 | `.github/workflows/release.yml`: удобный ручной `workflow_dispatch` с существующим release-тегом. Workflow разрешает тег в конкретный commit SHA, проверяет его принадлежность основной ветке и совпадение версии; запускает обязательные проверки именно этого SHA через общий CI workflow/скрипты. Релиз нельзя публиковать на основании зелёной проверки другого commit. |
| REL-02 | После успешных проверок Actions создаёт GitHub Release в текущем закрытом репозитории: release notes из changelog, инструкция обновления/миграций, backend wheel/sdist, SDK wheel/sdist, архив frontend build, manifest с версиями и commit SHA, SHA-256 контрольные суммы. Prerelease помечается соответствующим образом. Публичный PyPI и смена видимости репозитория не входят в процесс. |
| REL-03 | Сначала собрать и проверить все артефакты, затем загрузить их в draft release и опубликовать только после проверки полноты. Повторный запуск безопасно продолжает свой незавершённый draft либо сообщает конфликт; опубликованные файлы не заменяет. Права `contents: write` выдавать только job публикации; проверкам достаточно чтения. Исключить гонки выпусков одного тега. |
| CD-01 | Подготовить содержательный шаблон GitHub Actions CD, но **временно закомментировать все его строки**, включая триггеры и jobs. Хранить в `deploy/github-actions/cd.yml.example` вне `.github/workflows/`, чтобы не создавать невалидный активный workflow. Одного `if: false` или ручного триггера вместо комментариев недостаточно. |
| CD-02 | Комментарии CD описывают развёртывание уже проверенного release-артефакта по точной версии/контрольной сумме, целевое environment, секреты, миграции с backup, health check и процедуру отката с учётом совместимости схемы БД. Не угадывать адреса серверов и credentials; явно обозначить параметры, зависящие от будущей инфраструктуры. |
| CD-03 | CI и release не выполняют deployment. Активация CD — отдельное будущее изменение: определить инфраструктуру, заполнить настройки, проверить environment protection, раскомментировать и перенести шаблон в `.github/workflows/`. До этого ни push, ни tag, ни release, ни ручной запуск не должны приводить к развёртыванию. |

Реализация системы релизов входит в цель; фактический выпуск выполняется по поручению владельца. До него проверять процесс в режиме dry-run без создания тегов/релизов, проверять артефакты и синтаксис workflow. Dry-run не выдавать за реальный GitHub Release. Если GitHub Actions недоступен в текущей среде, явно отметить непроверенный удалённый запуск.

### 5.1. Обязательная документация по ходу работы

- `DOC-TRACK-01`: создать `docs/plan.md`, `docs/worklog.md` и `docs/status.md` до начала реализации приложения. Перед каждой рабочей сессией прочитать их и сверить с репозиторием; продолжать с фактического состояния, не начинать план заново.
- `DOC-TRACK-02`: до существенного этапа записать планируемый результат, способ проверки и ближайшие шаги. У задач стабильные ID, например `TASK-001`, и статусы `planned`, `in_progress`, `blocked`, `done`, `cancelled`. При смене плана сохранять причину; отменённые задачи не удалять бесследно. Прогнозы сроков отделять от фактических дат; не выдумывать срок, если его нельзя обосновать.
- `DOC-TRACK-03`: после каждого законченного смыслового изменения, проверки, смены плана или обнаружения блокера добавить запись в журнал и синхронизировать план/статус. Делать это в ходе работы и перед завершением сессии, передачей задачи или подготовкой commit/PR; итогового отчёта в чате недостаточно. Не требуется протоколировать каждый вызов инструмента.
- `DOC-TRACK-04`: запись журнала содержит время события в ISO 8601 с часовым смещением (например `2026-09-24T14:30:00+03:00`), исполнителя (Codex, Antigravity или человек), ID задачи/требований, выполненные действия, затронутые файлы, проверку и её фактический результат, оставшиеся вопросы и следующий шаг. Время брать из часов среды; неизвестное историческое время отмечать как неизвестное, не подставлять вымышленное.
- `DOC-TRACK-05`: у завершённой задачи есть фактические начало/завершение и доказательство выполнения её критерия; непроведённые проверки явно отмечены. Если обязательная проверка не выполнена, задача не получает `done`. У блокера указаны причина, попытки устранения и условие разблокировки. После вынужденного прерывания недостающую запись восстановить при возобновлении с пометкой о восстановлении.
- `DOC-TRACK-06`: журнал вести добавлением записей; ошибки исправлять отдельной корректирующей записью со ссылкой на исходную. План и статус обновлять как актуальные представления. Не заменять журнал `CHANGELOG.md`: changelog описывает выпуски, журнал — ход разработки. Не писать секреты, персональные данные, скрытые рассуждения или полные сырые логи; сохранять краткие факты и основания решений. Ссылки на commits/PR/CI добавлять только после их появления.
- `DOC-TRACK-07`: в README добавить ссылки на план, журнал и статус. Приёмка включает проверку согласованности этих документов с кодом, тестами и `docs/acceptance.md`; наличие файлов без содержательных своевременных записей не считается выполнением требования.

## 8. Порядок контроля и критерии завершения

Цель завершена только при выполнении всех пунктов:

- [ ] Чистая установка и запуск по README успешны; миграции применены на пустой PostgreSQL и проверены на обновлении схемы с тестовыми данными.
- [ ] Два клиента проходят OIDC SSO; проверены неверный redirect URI, state/nonce/PKCE, повторный code, неверная подпись/audience/issuer, истёкший токен, refresh replay и смена ключей.
- [ ] Обычный вход работает в default-профиле без SMTP, TOTP, Passkey и Recovery codes.
- [ ] Каждая из четырёх функций полностью проходит enabled-сценарий; при default-off недоступны её API и UI и отсутствуют побочные эффекты. Проверены недопустимые сочетания флагов и отключение уже используемого фактора.
- [ ] PostgreSQL-тесты доказывают одноразовость кодов при конкурирующих запросах; WebAuthn проверен с виртуальным аутентификатором и отрицательными challenges/origins.
- [ ] Тесты RBAC/IDOR, CSRF, блокировки пользователя, отзыва сессий, повторной аутентификации и редактирования администратора проходят.
- [ ] React собирается; браузерные E2E покрывают пользовательский и административный путь, оба профиля функций и два клиента. Проведена визуальная проверка desktop/mobile и клавиатуры.
- [ ] SDK собран и установлен из wheel в чистую среду; документированные примеры запускаются без импорта кода сервера.
- [ ] CI проходит обязательные проверки; сведения о найденных уязвимостях и принятых исключениях приложены без секретов.
- [ ] CI определён в GitHub Actions для PR и основной ветки; отчёт различает локальные проверки и реальные удалённые прогоны. Версии компонентов и тега согласованы, команда подготовки версии и changelog проверены.
- [ ] Процесс release проверяет точный SHA, блокирует несовпадение версии/неуспешный CI, собирает полный набор артефактов и контрольных сумм; dry-run и повторный запуск проверены без фактической публикации. Реальный выпуск, если поручен, подтверждён ссылкой на GitHub Release.
- [ ] Весь шаблон CD закомментирован и расположен вне активных workflows; CI проверяет это ограничение. Документированы будущая активация, секреты, миграции, health check и откат; активных путей deployment нет.
- [ ] Backup/restore воспроизведён на отдельной БД; задокументированы ротация ключей, откат и ограничения глобального logout.
- [ ] Документы из раздела 5 содержательны, ссылки и команды проверены; все ID требований связаны с результатами в `docs/acceptance.md`.
- [ ] План, журнал и статус велись по ходу работы: видны запланированные и выполненные задачи, фактические даты, проверки, изменения решений и блокеры. Статусы соответствуют доказательствам; сохранена понятная точка продолжения либо зафиксировано завершение.
- [ ] Итоговый отчёт различает реализованное, протестированное локально и ещё не проверенное в production. Нет фиктивных результатов или незакрытых обязательных пунктов.
