# Чек-лист текущей приёмки ALXPRGS SSO

Продукт 0.2.0; подготовлен 06.10.2026. Все пункты ниже ожидают отдельного runtime-прогона; заполненные отметки исторического раздела не переносятся на новую ревизию. Запишите SHA, профиль, стенд и результаты в acceptance.md.

## Текущие сценарии

- [ ] Чистый isolated Compose: owner/runtime/migrator, head0010, health/live и health/ready, bootstrap и повтор без изменения данных.
- [ ] Open-регистрация: условия/согласие, HTTP202 pending; неверный код/replay отказ; после настоящего email — User и обычный login. Closed — отказ без письма.
- [ ] Login/logout, cookie/CSRF/exact Origin; настроенный фактор до полной сессии; временный admin пароль → обязательная смена → новый login.
- [ ] Default-off: прямые MFA API404 и скрытый UI; email обязателен. Enabled: TOTP/UV Passkey/Recovery положительные и отрицательные случаи, без bypass.
- [ ] Два RP: state/nonce/PKCE, второй вход с OP session; logout OP не обещает back-channel отзыв всех RP.
- [ ] Admin RBAC/IDOR, последний администратор, session revoke, scopes и одноразовый secret; reauth/action/body-bound proof.
- [ ] Privacy/legal gates; request/cancel/deadline/worker, retention и restore с актуальным deletion journal на отдельной БД.
- [ ] Keyboard/mobile/theme footer/cookies/dialog, CSP за Nginx, reduced motion; fixtures отдельно от настоящего входа.
- [ ] SDK wheel/sdist, чистая установка, JWKS/claims/ошибки и запуск двух примеров.
- [ ] CI/release на нужном SHA, security scans, внешний HTTPS/OIF/mail/Sentry/owner review по применимым критериям.

## 2. Результаты выполнения сценариев

### Сценарий 1: Чистый запуск и инициализация мастера (SETUP-01..09)
- [x] **1.1. Запуск без существующего .env**: Подтверждена генерация безопасных секретов (`SESSION_SECRET_KEY`, `TOTP_ENCRYPTION_KEY`) в `start.ps1` / `start.sh` без перезаписи существующего `.env`.
- [x] **1.2. Проверка здоровья сервисов**: Контейнеры `db`, `backend`, `frontend` запущены в Docker Compose. Эндпоинты `/health/live` (HTTP 200) и `/health/ready` (HTTP 200, db connected) подтверждены.
- [x] **1.3. Мастер первого администратора**: Успешно выполнен `bootstrap_admin` в контейнере `alxprgs-sso-backend`, создан пользователь `compose_admin` с ролью `admin`.
- [x] **1.4. Проверка повторного запуска мастера**: Повторный запуск завершается с кодом 0, подтверждая идемпотентность и неизменность учетных данных и паролей (`test_bootstrap_pg.py`).

### Сценарий 2: Самостоятельная регистрация пользователя (REG-01..08)
- [x] **2.1. Регистрация в открытом режиме (`open`)**: В тесте `frontend/e2e/sso.spec.ts` выполнена регистрация нового пользователя через UI. Запись создана в PostgreSQL со статусом `is_active=True` и ролью `user`.
- [x] **2.2. Запрет регистрации в закрытом режиме (`closed`)**: При `registration_mode=closed` страница `/login` скрывает ссылку на регистрацию, а прямой вызов `POST /api/v1/auth/register` возвращает HTTP 403 Forbidden.
- [x] **2.3. Валидация и коллизии**: Попытка повторной регистрации существующего пользователя возвращает нейтральный 409 Conflict (`user_already_exists`) без раскрытия признака совпадения. Проверена минимальная длина пароля.
- [x] **2.4. Полномочия нового пользователя**: Вход под зарегистрированным обычным пользователем открывает личный кабинет, ссылка и доступ к админке скрыты, прямой запрос к `/api/v1/admin/*` возвращает 403 Forbidden.

### Сценарий 3: Личный кабинет и сессии (USR-01..06, ARCH-03..05)
- [x] **3.1. Вход и установка cookie**: При входе выставляется Host-Only сессионная cookie `alx_session` (или `__Host-alx_session` при HTTPS), `HttpOnly`, `SameSite=Lax`.
- [x] **3.2. CSRF-токен**: Возвращается заголовок `X-CSRF-Token`, мутирующие запросы без корректного токена блокируются (403 Forbidden). Защита охватывает также `/api/v1/auth/logout`.
- [x] **3.3. Просмотр активных сессий**: Эндпоинт `/api/v1/auth/me` и профиль пользователя корректно отображают статус текущей сессии.
- [x] **3.4. Отзыв сессий**: Проверена смена пароля: текущий пароль проверяется через Argon2id, после смены все сторонние сессии пользователя в PostgreSQL немедленно аннулируются (`test_auth_sessions_pg.py`).

### Сценарий 4: Панель администратора (UI-03, USR-07..09, AUDIT-01..03)
- [x] **4.1. Доступ к админ-панели**: Администратор успешно переходит во вкладку управления; обычный пользователь получает 403.
- [x] **4.2. Управление режимом регистрации**: Переключение режима `closed` -> `open` и обратно на панели управления требует повторного подтверждения пароля текущего администратора (`BUG-009` устранён).
- [x] **4.3. Управление пользователями**: Проверено создание пользователей, блокировка/разблокировка и аудит действий в `test_admin_api.py`.
- [x] **4.4. Защита последнего администратора**: Попытка деактивировать или лишить прав единственного активного администратора блокируется ошибкой 400 (`test_admin_api.py`, `test_auth_sessions_pg.py`).
- [x] **4.5. Управление OIDC-клиентами**: Создание клиента, однократный показ секрета при создании (`test_admin_api.py`).
- [x] **4.6. Журнал аудита**: В PostgreSQL фиксируются все значимые события (`login_success`, `login_failed`, `registration_mode_changed`, `auth_code_replay_detected`).

### Сценарий 5: Сквозной SSO для двух независимых клиентов (SSO-01..07, SDK-06)
- [x] **5.1. Авторизация в Клиенте 1**: Генерация URL с PKCE S256 verifier/challenge, перенаправление на SSO, обмен кода на токены в `test_oidc_pg.py`.
- [x] **5.2. Бесшовный вход в Клиент 2**: При наличии активной сессии SSO обращение от Клиента 2 завершается мгновенным выпуском authorization code без запроса пароля (`test_oidc_pg.py`, `test_sso_cross_clients.py`).
- [x] **5.3. Выход из SSO (Logout)**: Запрос RP-initiated logout инвалидирует сессию в PostgreSQL.

### Сценарий 6: Четыре отложенных механизма (Default-off vs Enabled)
- [x] **6.1. Default-off профиль**: Все прямые вызовы к TOTP, Passkey, Recovery Codes, Email verification возвращают 404 `feature_disabled`. На фронтенде элементы скрыты (`01. Default Profile` E2E).
- [x] **6.2. Enabled TOTP**: В enabled-профиле проверен выпуск секрета TOTP, шифрование в PostgreSQL через Fernet и `TOTP_ENCRYPTION_KEY`, подтверждение кодом pyotp и активация.
- [x] **6.3. Enabled WebAuthn Passkey**: Проверены генерация options для регистрации и аутентификации, валидация challenge и обработка учетных данных WebAuthn.
- [x] **6.4. Enabled Recovery Codes**: Выпуск 10 кодов, проверка зависимости от активного TOTP (SEC-FLAG-05), успешное сгорание кода при входе, запрет повторного использования (одноразовость).
- [x] **6.5. Enabled Email Verification**: Выпуск токена в локальный `sent_emails_sink` без отправки реальных писем (SEC-FLAG-07), подтверждение через эндпоинт, блокировка входа при `REQUIRE_VERIFIED_EMAIL=true` до подтверждения.
