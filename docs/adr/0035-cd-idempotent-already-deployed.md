# ADR-0035: Идемпотентный EC2 CD для уже установленного SHA

Дата: 29.10.2026. Статус: принято; CD-IDEMPOTENCY-01.

## Причина и решение

Повторный запуск CD для уже исправно установленного commit SHA заново собирал образы,
проверял transport и выполнял полную серверную установку. SemVer, номер run, дата сборки,
Docker-тег, статус прошлого workflow и SHA последней попытки не доказывают, какая ревизия
реально работает: одна версия продукта соответствует нескольким коммитам.

Решение — два независимых уровня проверки полного commit SHA:

1. Preflight до тяжёлой сборки. GitHub runner обращается только к фиксированному
   `https://auth.alxprgs.tech` с обязательной проверкой TLS, без redirects и proxy,
   с timeout 15 секунд и лимитом ответа 4096 байт. Backend `/health/identity` должен
   вернуть `200` с точным JSON, `database=connected` и полным SHA; frontend
   `/build-info.json` должен подтвердить тот же SHA. Оба ответа обязаны иметь
   `Cache-Control: no-store`. Совпадение даёт `already_deployed` и пропускает build,
   verify, transport и install. Любое неизвестное состояние продолжает обычный
   защищённый deploy, а ошибка TLS/redirect/чужого origin является security error.
2. Серверная повторная проверка внутри существующей flock-блокировки перед первым
   побочным эффектом. `ssoctl deploy` сверяет `deployed.json`, `current/manifest.json`,
   `current/public/build-info.json`, отсутствие maintenance, запущенный backend
   container (image ID, service и config_files labels) и локальный `/health/identity`.
   Только полное согласие даёт no-op: без распаковки, `docker load`, backup, миграций,
   перезапуска, переключения `current`, reload nginx и уведомления.

`highwater.json` остаётся защитой от устаревшего sequence, но не доказательством
успешной установки: он пишется до изменений сервера. No-op не обновляет sequence и не
разрешает установку устаревшей ревизии.

## Результаты и протокол

Workflow различает `deployed`, `already_deployed`, `superseded` и ошибку. `ssoctl deploy`
выводит ровно одну машинную строку `ssoctl-result:{"version":1,"result":...}`; `upload.sh`
передаёт её в `scripts/deploy_result.py`, а не разбирает человекочитаемый текст. Только
`deployed` даёт `installed=true`. Старый оператор без протокола явно маркируется
`deployed_legacy`: его успешный exit всегда означал реальную установку, но серверная
no-op защита не активна до установки нового `/opt/alxprgs-sso/tools/ssoctl.py`.

## Альтернативы и последствия

- Сравнивать VERSION или Docker-тег — неверно: разные коммиты могут иметь одну версию.
- Доверять только frontend `build-info.json` — недостаточно: не проверяет backend,
  запущенный контейнер и readiness.
- Доверять только `deployed.json` — недостаточно: запись может пережить повреждённое
  или частично откатанное состояние; нужны manifest, frontend, контейнер и HTTP identity.
- Новый endpoint `/health/identity` выбран вместо расширения `/health/ready`, чтобы
  сохранить существующий контракт мониторинга и public-check.
- Preflight не может полностью исключить гонку: main может продвинуться, а другой run
  установить SHA между проверкой и установкой. Поэтому серверная проверка под блокировкой
  обязательна; ранняя проверка — только оптимизация.
- Обновление root-owned оператора не автоматизируется: оно требует проверенного SHA,
  точных файлов/команд и выполняется владельцем отдельно; workflow до обновления
  безопасно работает в режиме `deployed_legacy`.
- Кэширование identity недопустимо: отсутствие `no-store` трактуется как
  неподтверждённое состояние, а не как совпадение.
