# ADR-0033: Повтор отдельных стадий EC2 CD

Дата: 26.10.2026. Статус: принято; CD-STAGES-01.

## Причина и решение

Единый job повторно собирал приложение после внешнего сбоя установки на сервере.
Разделить workflow на build → verify → deploy. Передавать transport через приватный
неизменяемый Actions artifact текущего run, хранение 7 дней. Имя включает run ID и
attempt build, передаётся через outputs успешного build; полный повтор не перезаписывает
прежний artifact. ID также сохраняется в outputs. Закреплённый download-artifact v4.1.9
поддерживает точное имя, но не artifact-ids; используем существующую версию без обновления.
Deploy зависит от успешного verify; оба используют одно имя и checkout исходного SHA.
Environment production и SSH secrets доступны только deploy. Freshness main перед
сборкой и установкой, последовательность run и серверная политика rollback сохраняются.

## Альтернативы и последствия

Единый job проще, но повторяет дорогую сборку. Registry добавляет отдельный контур
хранения; кэш сборки не гарантирует использование того же проверенного архива.
Выбран artifact с ограниченным сроком: после удаления нужен полный повтор build/verify.
Повтор deploy повторяет всю серверную транзакцию, не отдельную команду миграции.
GitHub Actions live-проверка повторов требуется после интеграции; локальные policy tests
проверяют зависимости и контракты workflow, но не имитируют выполнение GitHub scheduler.

Дополнение CD-PUBLIC-CHECK-01: последним отдельным job public-check проверять
HTTPS /health/ready с внешнего GitHub runner (HTTP 200 и database connected).
Job зависит от успешного deploy и его output installed=true, установленного только после
успешного upload.sh. Пропущенный устаревший deploy не объявляется доступным.
Проверка TLS обязательна; redirects/retries отсутствуют. Повтор public-check не вызывает
повторной установки и не выполняет rollback. Сам endpoint уже реализован в backend.
