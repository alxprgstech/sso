Commit/push и удалённые workflow выполнять только в пределах явно доступной авторизации владельца; не считать ссылку на старый чат доказательством разрешения. ## 4. Обязательные пакеты работ

### G8-SEC — Устранить нарушения доверия (P0)

Начни с FINAL-01..04 аудита; они не исправлены подготовкой этого файла.

- Confidential client: отсутствие, пустой и неправильный secret должны отклоняться на code exchange, refresh и revoke независимо от формы передачи. Public client с правильным PKCE работает без секрета. Проверить Basic/form, деактивацию клиента и отсутствие расходования валидного code при неверной аутентификации согласно выбранной протокольной политике.
- Authorization endpoint: использовать общую проверку абсолютного/idle TTL, отзыва, блокировки и требуемого уровня аутентификации; не выдавать code по устаревшей cookie. Зафиксировать отрицательные HTTP+PostgreSQL сценарии.
- SDK: audience обязателен и проверяется по настроенному значению по умолчанию; issuer, подпись, алгоритм, обязательные exp/sub/aud/iss и тип токена проверяются строго; nbf/iat проверять согласно контракту. ID token и токен без обязательных claims не принимаются как access. Проверить malformed JWT/JWKS, unknown kid, сеть, TTL cache, ограничение частоты refresh; бесконечный stale cache запрещён. Ошибки типизированы, не содержат секретов.
- Login continuation: исключить внешний произвольный return_to/redirect_uri, protocol-relative, javascript/data и варианты кодирования; законное продолжение OIDC работает без расширения доверия ко всем поддоменам.
- Проверь аналогичные пути в API/SDK, scopes и roles, re-authentication, смену/сброс пароля и факторов. Обязательные отрицательные сценарии должны проверять поведение, а не текст реализации.

Готово: дефекты воспроизведены до исправления и соответствующие tests проходят после него, защита не обойдена, исправления привязаны к требованиям и diff.

### G8-SSO — Завершить протокольный контракт (P0/P1)

- SSO-01: реально использовать поддерживаемую OIDC/OAuth библиотеку в протокольной обработке; одного пакета authlib в dependencies недостаточно. Проверить официальную документацию, лицензии и совместимость до выбора/изменения зависимости. Собственные доменные правила и PostgreSQL storage сохранить.
- Discovery должен соответствовать реализованным endpoint/auth methods/алгоритмам. Точная регистрация redirect/logout URI, PKCE S256, state/nonce на стороне клиента, одноразовые codes и refresh replay обязательны.
- Ограничить scopes разрешёнными клиенту; email/profile claims выдавать только при соответствующем разрешении. Проверить token/UserInfo и отрицательные запросы scopes.
- Проверить абсолютный срок refresh family при ротации, блокировку пользователя, отзыв и связь с сессиями. Задокументировать окно автономного access JWT не более 5 минут.
- SSO-06: работающая ротация signing keys с kid и периодом перекрытия; текущий и предыдущий публичные ключи доступны в допустимый период, старый ключ после периода удаляется, неизвестный kid отклоняется. Проверить два процесса и restart с общими стабильными ключами; генератор пары ключей не является доказательством ротации.
- Повторная аутентификация/MFA чувствительных операций, защита последнего администратора при конкурентных изменениях, fail-closed при недоступности БД. Сверить весь раздел 4 GOAL, включая логи/correlation ID и отсутствие секретов.

### G8-SDK — Закончить интеграцию и два клиента (P1)

- Реализовать SDK-03 start/callback/logout с серверной web-сессией, одноразовыми state/nonce/PKCE, TTL и привязкой к инициировавшему браузеру; корректная проверка ID token и nonce. Не выдавать bearer/refresh в HTML/JSON браузерного callback и не хранить их в localStorage.
- Два отдельных FastAPI примера с разными client IDs, согласованными issuer/адресами и безопасными настройками. In-memory demo не выдавать за промышленное распределённое хранилище; выбранное хранилище/ограничения должны соответствовать ТЗ и тестам.
- Из wheel в чистой среде без backend imports: API integration в 3–5 строк, 401/403/roles/scopes, web login/logout, типизированные ошибки, JWKS rotation/cache, negative tokens.
- В Playwright поднять настоящий SSO и оба примера: первый вход с паролем, переход во второй без повторного пароля, локальные сессии, выход и документированные ограничения глобального logout. Проверить state/nonce mismatch, replay callback и привязку к другому браузеру. Моки теста test_sso_cross_clients не заменяют этот E2E.

### G8-UI — Закончить пользовательские процессы (P1)

- Убрать заглушку handleMfaSubmit. Enabled: TOTP enrollment с подтверждением, вход, удаление с re-auth; recovery выпуск/замена/разовый показ/погашение после пароля; email request/resend/confirm, истечение/replay, смена адреса и обязательный email до входа. Письма только в локальный SMTP sink. Passkey сохранить с реальным виртуальным аутентификатором и UV.
- UI-02/03/04: профиль, смена пароля, свои сессии; админ-редактирование пользователей/ролей/клиентов/redirect URI, отзыв, разовый секрет, audit filters/pagination. Проверить не только наличие кнопки, но и её API/права/ошибки.
- Default-off: функциональные controls скрыты, прямые API недоступны, нет писем/побочных эффектов. Enabled и REQUIRE_VERIFIED_EMAIL=true — отдельные полноценные сценарии. Недопустимые комбинации и отключение обязательного фактора проверяются без bypass.
- Desktop/mobile, клавиатура, focus, labels, ошибки и loading. Добавить содержательные component tests и browser E2E на законченные процессы, включая обычного пользователя и администратора. Не требуются новый дизайн или визуальные украшения вне ТЗ.

### G8-CI — Воспроизводимые обязательные проверки (P1)

- Закрепить Python runtime/tooling/dependencies в lock-механизме; применять его в локальных инструкциях, CI и сборках. Не менять версии произвольно и не заявлять актуальность без проверки официальных источников.
- CI PR/main: Ruff включая scripts и SDK, Python typecheck, unit + настоящая PostgreSQL integration, миграции, SDK wheel/sdist + clean install/examples, ESLint/TypeScript/component tests/build, browser default-off/enabled и два клиента, dependency/secret scanning. При переносе тестов в отдельный job сохранить обязательность и coverage.
- Полные SHA Actions, минимальные permissions, timeout и срок хранения артефактов; никаких production secrets в PR. Сканировать реально поставляемые зависимости, документировать findings и даты. Critical/high не принимать самостоятельно; решение об исключении — владельцу, остальную работу продолжать.
- Исправить первопричины сбоев Linux/Windows и lifecycle; никаких retries для сокрытия ошибок. Сохранять logs/trace без секретов при ошибках.

### G8-REL — Безопасная подготовка выпуска без публикации (P1)

- Исправить FINAL-07. Сначала безопасно разрешить существующий tag в SHA, затем читать VERSION и метаданные именно того commit. Пользовательский input передавать через env/аргументы, не вставлять прямо в shell source.
- Общий CI workflow/скрипты обязаны проверять выпускаемый SHA, а не SHA запуска workflow. Dry-run выполняет те же проверки и сборку, но не создаёт release/тег и не публикует.
- Набор: backend wheel/sdist, SDK wheel/sdist, frontend archive, release notes из соответствующего changelog, migration/update instructions, manifest с SHA/версией, SHA-256. Проверить содержимое пакетов: нужные миграции/конфигурация/инструкции должны быть доставляемы по документированной процедуре.
- Publish job получает только проверенный комплект, создаёт draft, загружает и проверяет полноту/контрольные суммы; только затем возможна публикация при отдельном поручении. Безопасный повтор своего draft, отказ при конфликте/опубликованной версии, отсутствие перезаписи. Write permission только публикации.
- Проверить mismatched version/tag, отсутствующий тег, непройденные tests, неполный/испорченный комплект и повторный запуск без внешней публикации. Если подходящего существующего тега нет, локально проверить сборочный путь и честно оставить удалённый tag dry-run blocked; не создавать релизные теги без поручения.
- SemVer/PEP 440, единая команда подготовки версии и changelog. Не повышать до 1.0.0 ради формального завершения. CD остаётся полностью закомментированным вне workflows, тест этого условия обязателен.

### G8-OPS — Эксплуатация и достоверность длительного теста (P1)

- Чистый Compose из документированных файлов на новой изолированной БД, bootstrap без пароля по умолчанию, повторный запуск без потери данных, health/readiness, fail-closed при сбое БД.
- Миграции пустой и предыдущей схемы с synthetic data; backup/restore в отдельную БД, живой вход, сохранение ролей/сессий/клиентов и восстановление TOTP с отдельно сохранённым ключом. Не объявлять --help доказательством восстановления.
- После исправлений runtime выполнить 5 lifecycle/browser циклов, конкурентные проверки по 10 попыток для каждого сценария GOAL-07 и один непрерывный soak >=1200 секунд. Старые прогоны не засчитывать изменённому runtime.
- Проверить сам runner: нагрузка включает разрешённый code/token flow и SDK, а не только discovery/JWKS/login. Summary содержит SHA, dirty-state или hash patch, версии среды, seed, реальную длительность нагрузки, scheduled/executed smokes, PID и свидетельство его владения сокетом, память, PG baseline/final, неожиданные/ожидаемые ошибки. Не дописывать измерения задним числом.
- При первом новом неожиданном сбое остановить повторяющуюся группу, диагностировать, исправить и повторить затронутое. Не делать бесконечные одинаковые прогоны. После завершения очистить только собственные ресурсы.
