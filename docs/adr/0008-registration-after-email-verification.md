# ADR 0008: создание самостоятельной учётной записи после подтверждения email

> Сверка 06.10.2026: сохранено решение на дату принятия; это не новый результат приёмки. Действующий профиль: [архитектура](../architecture.md), [API](../api.md), [статус](../status.md).

- Статус: принято по прямому поручению владельца, 2026-09-29.
- Контекст: прежний `AuthService.register_user` создавал активного пользователя до доставки письма; флаг `FEATURE_EMAIL_VERIFICATION_ENABLED=false` позволял регистрацию без подтверждения. Владелец изменил это требование для самостоятельной регистрации.
- Решение: запрос регистрации создаёт ограниченную по времени заявку с хешем пароля, шестизначным кодом и независимой одноразовой ссылкой. Запись `users` создаётся только при атомарном подтверждении через PostgreSQL. Существующий email-процесс для уже созданных пользователей и политика их входа остаются совместимыми.
- Безопасность: низкоэнтропийный код хранится только как HMAC с ключом, производным от серверного секрета; число попыток и повторных отправок ограничено в БД, ссылка хранится как SHA-256. Подтверждение блокирует строку заявки, затем создаёт пользователя и погашает заявку одной транзакцией. Рендер страницы по GET не подтверждает адрес.
- Альтернативы: создание `users` с `email_verified=false` отклонено, поскольку требование запрещает завершить регистрацию до подтверждения; только ссылка отклонена, поскольку владелец запросил шестизначный код; геолокация по стороннему API отклонена из-за утечки IP и требования использовать только доверенный прокси.
- Последствия: контракт `/auth/register` меняется с `201` и `user_id` на `202` и `challenge_id`; клиенты должны завершать отдельный шаг. Старые пользователи, ранее выданные ссылки и политики их входа не мигрируются автоматически.
