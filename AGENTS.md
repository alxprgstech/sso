# Правила Codex и Antigravity для ALXPRGS SSO

Выполняй текущую задачу пользователя; не запускай весь проект и старые задачи автоматически. Указания пользователя и среды имеют приоритет. Единственный корневой файл правил — `AGENTS.md`; не создавай копии для разных агентов.

## Контекст и границы

- Закрытый проект: FastAPI/Python, PostgreSQL, React/TypeScript, отдельный Python SDK. Версия — `VERSION`; состояние продукта и запуск — README.
- Сохраняй чужие изменения. Рабочие ветки и PR — `new/<задача>`, не `codex/` и не отдельная `new`.
- Локальная реализация, тестовые контейнеры и документация входят в порученную разработку. Production, DNS, расходы, публикация, реальные рассылки и разрушение пользовательских данных требуют соответствующего поручения. Разрешения активного CD описаны в тематических правилах.
- Не создавай дополнительные чаты или агентов без запроса либо явного применимого правила. Не меняй глобальные настройки инструментов. Не спрашивай повторно о разрешённой обратимой работе.

## Чтение и учёт

1. Для изменений проверь `git status` и прочитай [текущий статус](docs/status.md). В README и документации читай только разделы по задаче; навигация — [docs/index.md](docs/index.md).
2. В [плане](docs/plan.md) ищи текущий ID. [Журнал](docs/worklog.md), архивы и ADR читай выборочно по ID или вопросу; полное чтение истории не требуется. Исторические статусы и PASS не подтверждают текущую ревизию.
3. Консультации, анализ и review без изменения файлов не требуют новой записи в плане, журнале и статусе. Мелкая редакторская правка без изменения требований допускает только итоговый отчёт и commit.
4. До существенного изменения запиши в плане ID, приоритет, зависимости, критерий готовности, статус и фактическое начало. Краткую запись старта добавь в журнал. Существенное архитектурное решение обоснуй в ADR с альтернативами.
5. Промежуточный учёт нужен при существенном изменении плана, блокере или передаче/прерывании работы. Не обновляй три реестра после каждой правки, проверки или перед каждым commit.
6. При завершении обнови статус задачи в плане и добавь итог в журнал: время ISO 8601 с часовым смещением из часов среды, исполнитель, ID, изменения/файлы, фактические проверки, ограничения и следующий шаг. В статусе сохрани краткую точку продолжения со ссылками; не копируй подробные результаты между реестрами.
7. Статусы: `planned`, `in_progress`, `blocked`, `done`, `cancelled`. Для `done` нужны критерий и обязательные проверки; для blocked — условие разблокировки, для отмены — причина. Журнал дополняй, историю не переписывай; восстановленные после прерывания сведения помечай явно.

План хранит задачи; статус — актуальный срез; журнал — хронологию; acceptance — доказательства общей приёмки. Завершённые этапы и прежние срезы отделяй в историю, сохраняя ID, результаты и ссылки. Архив не входит в обязательное стартовое чтение. Открытые требования не отменяются архивированием.

## Неизменяемые требования безопасности

- Не ослабляй защиту или достоверность тестов ради зелёного результата, включая dev/CI. Не отключай TLS, подписи/claims, PKCE/state/nonce, CSRF/RBAC, reauth, MFA/email, лимиты, одноразовость и отзыв. Не скрывай ошибки skip/xfail, retries или подменой реального теста моками.
- TOTP, Passkey, Recovery codes и `REQUIRE_ADMIN_MFA` включены по умолчанию, включая отсутствие env. Самостоятельная регистрация требует подтверждения email; `FEATURE_EMAIL_VERIFICATION_ENABLED=false` запрещён. Обычный пользователь без подключённого фактора может войти по паролю; настроенный фактор нельзя обходить отключением флага.
- Административные API и выдача admin-роли OIDC требуют серверного `Session.mfa_verified`. Recovery codes требуют подтверждённый TOTP или Passkey, одноразовы и не участвуют в external step-up.
- WebAuthn требует user verification и точных origin/RP ID/challenge/подписи. Запрещены `require_user_verification=False` ради теста, расширение доверенных origins и повтор проверки с альтернативным RP ID.
- Не коммить и не выводи секреты, реальные персональные данные, дампы и ключи. Не реализуй собственную криптографию; не принимай ID token как access token. Подробные протокольные и тестовые инварианты обязательны при работе с соответствующим кодом.

## Pull request

Заголовок и описание PR пиши на русском; технические имена, команды и общепринятые термины сохраняй. Указывай только полезные для ревью сведения: проблему, итоговое изменение, фактические проверки и существенные ограничения. Подробности оформления — [правила PR](docs/agent-policies.md#правила-pull-request).

## Проверка и завершение

- Реализуй законченный сценарий без неиспользуемых абстракций; запускай относящиеся к изменению проверки. Исправление ошибки сопровождай содержательным regression test, когда он проверяет реальное поведение.
- Для редакторской правки достаточно проверить ссылки, согласованность и изменённые примеры; полный набор приложения не нужен. Полная приёмка остаётся обязательной перед объявлением общей цели выполненной.
- Изменения API/схемы/настроек сопровождай актуализацией соответствующей документации; матрицу приёмки обновляй при изменении её критериев или получении новых доказательств, не при каждой правке.
- Отчитывайся по-русски: сделано, проверено, не проверено/заблокировано. При блокере укажи наблюдаемую ошибку без секретов и минимальный следующий шаг. Отсутствие среды не является успешной проверкой.
