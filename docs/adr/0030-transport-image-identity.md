# ADR-0030: Идентичность образов транспорта между image stores

Дата: 25.10.2026. Статус: принято в задаче DEPLOY-EC2-01 (инцидент CD run 6, SHA b1236e01).

## Решение

Идентичность образов в EC2 transport — config-digest образов, извлечённый из самого
`images.tar` при сборке бандла. Раннеры CD/CI принудительно переключают Docker на классический
image store (`features.containerd-snapshotter=false` в daemon.json + restart), тот же store
использует сервер. PostgreSQL, скачиваемый по digest, получает явный тег
`alxprgs-sso-postgres:<префикс digest>` и сохраняется в архив по тегу вместе с backend.
Проверка transport на раннере после `docker load` репетирует серверную проверку: оба
manifest-ID обязаны существовать как ID образов. Неожиданный формат архива (OCI вместо
classic docker-archive) или неожидаемый набор образов — жёсткий отказ сборки бандла.

## Причина

Раннеры GitHub ubuntu-24.04 по умолчанию используют containerd image store: `docker image
inspect .Id` возвращает digest манифеста, `docker save` пишет OCI-архив. Сервер EC2
(docker-ce, классический store) назначает загруженным образам config-digest ID. В CD run 6
manifest записал backend как digest манифеста (sha256:0d73b1a…), сервер загрузил тот же образ
с config-digest ID (sha256:1d06636…), и `ssoctl deploy` упал на `docker image inspect`;
PostgreSQL без тега вообще не пережил межstore-загрузку. Раннер-проверка не поймала расхождение:
она выполняется в том же containerd store, где manifest-ID разрешаются.

## Альтернативы и последствия

- Вычислять ID через `docker image inspect` раннера: неверно при любом дрейфе store; отклонено.
- Ссылаться в compose на теги вместо config-digest: работает на любом store, но ослабляет
  проверку идентичности и скрывает расхождение сред; отклонено.
- Парсить оба формата архива (OCI + classic): приняты только classic docker-archive; OCI —
  громкий отказ, потому что серверная семантика ID для OCI-архива не контролируется нами.
- Диагностика ssoctl дополнена argv неуспешной команды; stderr дочерних команд по-прежнему
  не выводится, секреты в argv этих команд отсутствуют по построению.

Обязательства: смена/удаление шага pin классического store в workflows отслеживается
policy-тестом; regression-тесты закрывают парсинг архива и репетицию идентичности.

Уточнение по факту 25.10.2026 (диагностика EC2 после sequence 9): сервер работает на
Docker 29.9.2, где свежая установка по умолчанию даёт containerd image store (`overlayfs`),
а не классический, как предполагалось выше. Подтверждено: оба образа нового бандла загрузились
с именами (тег PostgreSQL работает), но получили ID манифестов (backend `4d76954d…`,
postgres `e07f16af…`), не равные config-digest из manifest. Решение сохранено и завершено:
классический store закреплён **с обеих сторон** — раннеры CD/CI шагом workflow, сервер
однократной настройкой daemon.json; `bootstrap.sh` делает это автоматически для новых
установок (policy-тест расширен). Инструкция для существующего сервера — раздел 5
docs/ec2-deployment.md.
