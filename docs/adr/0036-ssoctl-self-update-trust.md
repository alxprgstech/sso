# ADR-0036: Доверие при самообновлении root-оператора ssoctl

Дата: 30.10.2026. Статус: принято; SSOCTL-SELF-UPDATE-01.

## Причина

`/opt/alxprgs-sso/tools/ssoctl.py` выполняется от root и управляет релизами,
конфигурацией, backup, сертификатами и восстановлением администратора. Обычный CD
обновляет приложение, но не установленный оператор. Ручная точечная замена работала,
однако требовала отдельной проверки файла и допускала ошибки при повторении. При этом
закрытый репозиторий нельзя читать анонимно, а загруженный код нельзя исполнять до
проверки.

## Решение

Самообновление читает один файл из одной фиксированной точки доверия:

- repository `alxprgstech/sso`, branch `main`, path `deploy/ec2/ssoctl.py`;
- GitHub REST API `https://api.github.com`; URL, repository, branch и path — константы,
  не переменные окружения и не аргументы командной строки;
- доступ — fine-grained personal access token только с `Contents: read` и
  автоматическим `Metadata: read` для этого репозитория. Токен хранится вне Git и
  `runtime.env` в `/etc/alxprgs-sso/github-read.token`: root-owned, mode `0600`,
  каталог `/etc/alxprgs-sso` — `0700`. Токен не является Resend, application или
  deploy SSH credential;
- TLS: `SSLContext(PROTOCOL_TLS_CLIENT)`, `CERT_REQUIRED`, hostname verification,
  фиксированный системный bundle `/etc/ssl/certs/ca-certificates.crt`. Переменные
  `SSL_CERT_FILE`/`SSL_CERT_DIR` не используются. Environment proxy отключён
  (`ProxyHandler({})`), redirects запрещены полностью, поэтому credential не может
  уйти на другой origin;
- timeout 20 секунд на запрос, лимит metadata-ответа 2 MiB, лимит файла 1 MiB.

Без `--sha` main разрешается в полный commit SHA **один раз**. Далее commit, сравнение
и файл запрашиваются только по этому неизменяемому SHA; продвижение main не смешивает
ревизии. С `--sha` принимается только полный 40-символьный lowercase hex; `commits/{sha}`
подтверждает идентичность коммита, а `compare/{sha}...main` — что `sha` является
ancestor/identical main (`status` `ahead`/`identical`, `merge_base_commit.sha == sha`,
`behind_by == 0`). Ветки, теги, сокращённые SHA и коммиты PR-веток отклоняются.

Файл проверяется по metadata (`type=file`, точный path, `encoding=base64`, размер) и
Git blob SHA (`sha1("blob <len>\0" + content)`), что обнаруживает повреждение или
подмену содержимого. Это проверка целостности, а не самостоятельный якорь доверия:
происхождение обеспечивают TLS до фиксированного GitHub origin, read-only credential
и закреплённый commit SHA, входящий в main.

До замены кандидат пишется в защищённый временный файл в каталоге назначения и
проверяется **без выполнения операций оператора**: синтаксис Python, `--help` целевым
`/usr/bin/python3` с timeout, наличие обязательных подкоманд, `recover-admin --help` и
`self-update --help`. Это выявляет конфликт argparse, который не видит один `compile`.
При совпадении содержимого команда успешно завершается без backup и замены.

Замена выполняется под существующей общей flock-блокировкой `operator.lock`, поэтому
не пересекается с deploy, backup, renew и другим self-update. Порядок: backup
действующего файла (root-only `0600`, уникальное имя, без перезаписи) → `chmod 0755`,
`chown root:root`, `os.replace` в той же файловой системе → проверка owner/mode/content
и `--help` установленной копии → при ошибке атомарное восстановление прежних байтов.
Symlink назначения или backup-каталога отклоняется. Временные файлы удаляются.

Команда не читает `runtime.env`, не обращается к Docker/application/release и не
запускает bootstrap, миграции, restart, nginx, тесты доставки или письма. Поэтому она
работает при недоступном приложении и без успешного release; оператор и приложение
обновляются независимо.

## Альтернативы

- **GitHub App installation token** — минимальные права и короткий срок жизни, но
  требуют private key, подписи JWT, выпуска/кэширования installation token и обработки
  clock skew. Для одного файла это существенно больше кода и секретов; отложено.
- **Deploy key + `git fetch`/`git show`** — нужен git на сервере, known_hosts и отдельный
  ключ; read-only deploy key даёт доступ ко всему репозиторию, а не к одному path.
  Дополнительная цепочка доверия не уменьшает риск по сравнению с fine-grained token.
- **Публичный raw URL или GitHub release artifact** — закрытый репозиторий не даёт
  анонимного чтения; artifact CD живёт ограниченное время и относится к другой задаче.
- **Токен в `runtime.env`/application env** — увеличивает blast radius, попадает в
  `app.env` и контейнер, противоречит разделению операторских и прикладных секретов.
- **`curl | sh`, `eval`, установщик из сети** — загруженный код исполнялся бы до
  проверки; запрещено.
- **Локальный SHA-256 как доказательство происхождения** — хеш, вычисленный из того же
  ответа, подтверждает только целостность; доверие к источнику он не создаёт.
- **Автоматическое обновление оператора из CD** — расширило бы права deploy-пользователя
  и смешало бы app CD с изменением root-owned tool; не принято.

## Последствия и ограничения

- Первый переход выполняется владельцем вручную по
  [инструкции](../ec2-deployment.md#обновление-установленного-ssoctl): установленный
  оператор может не иметь self-update и содержать дефект argparse. Дальнейшие
  обновления — `sudo ssoctl self-update` или `--sha`.
- Токен нужно создать и ротировать владельцу; при отсутствии, истечении или отзыве
  self-update завершается ошибкой до сети либо с HTTP 401/403 и не меняет оператор.
  Это влияет только на обновление оператора, не на приложение.
- Токен — bearer-credential с чтением закрытого репозитория. Компрометация позволяет
  читать код, но не менять репозиторий, не запускать CD и не получать application
  secrets. Токен не выводится, не передаётся в argv/URL и не логируется.
- Sudoers `ssodeploy` не расширяется: self-update доступен только root через обычный
  административный sudo. Wrapper и путь установки не меняются.
- Автоматический откат страхует неудачную установку, но не заменяет ручное
  восстановление из backup, если новый оператор не запускается.
