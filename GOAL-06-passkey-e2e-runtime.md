## 2. Baseline: факты и гипотезы

Владелец сообщил локальный успех backend/сборок/SDK, но браузерный прогон до отправки не выполнялся. Известные коммиты: `75fe796` и `5cd6866`. SHA нового упавшего run в приложенном тексте не указан: получить его и ссылку из GitHub, не угадывать.

Новый лог показывает **4 failed**:

1. Проверка enabled capabilities не находит «Включено» для Passkey.
2. Три следующих сценария доходят до ожидания `passkey-name-input` и падают по общему таймауту 45 секунд. До создания credential они не доходят.
3. Seed сообщает успех перед каждым тестом. Это доказывает лишь завершение подготовки, но не профиль процесса, к которому обращается браузер.

В прочитанном workflow оба профиля последовательно используют порт 8000; запуск записан как `cd backend && uvicorn … &`, PID берётся через `$!`. Остановка: `kill $(cat /tmp/backend.pid) || pkill … || true`. Возможная причина: PID принадлежит фоновому compound shell, `kill` успешно завершает оболочку, дочерний uvicorn остаётся, fallback не запускается. Enabled-процесс не занимает порт, а health-check отвечает от старого default-off процесса. **Это сильная гипотеза, требующая подтверждения PID/логами/ответом capabilities**, а не установленный факт нового run.

Также при чтении `WebAuthnService` обнаружены `require_user_verification=False`, расширенный список ожидаемых origins и повторная проверка с fallback RP ID. Проверить все ветки регистрации и аутентификации; наличие зелёного теста не оправдывает ослабление исходных требований.

## 3. G6-RUNTIME — управлять настоящими серверными процессами

- Воспроизвести точную последовательность workflow в изолированной среде, предпочтительно Linux с версиями runner. Не начинать с правок селекторов или увеличения timeout.
- До/после запуска и остановки сохранить безопасные PID/PPID, владельца listening socket, exit status и отдельные backend logs. Секреты окружения не печатать.
- Проверить, освобождён ли порт после default-off; завершился ли enabled сразу с address-in-use; совпадают ли HTTP capabilities с ожидаемым профилем. При недоступности старых артефактов воспроизвести ошибку и собрать новые.
- Выбрать надёжный lifecycle: отдельные jobs/стенды на разных портах или управляемые процессы с реальным PID/`exec`, корректным signal forwarding и ожиданием завершения. Не использовать глобальный `pkill` по имени, затрагивающий чужие процессы. PID-файлы и ресурсы привязать к test run.
- Проверять успешный старт, живость именно нового процесса и отсутствие startup failure. После timeout readiness — ненулевой exit code с логом, а не продолжение job. Остановка должна ждать подтверждённого завершения; cleanup работает и при падении браузерного теста.
- Сохранять безопасную изоляцию PostgreSQL и test DB guard. Стенды не должны использовать рабочие контейнеры/volumes или сбрасывать реальные аккаунты.

## 4. G6-PREFLIGHT — доказать профиль до запуска браузерных сценариев

- Перед default-off suite проверить capabilities: четыре флага false. Перед Passkey suite — Passkey true и явные остальные настройки, включая email policy. Ответ должен быть успешным JSON, а не только HTTP 200 от health/live.
- Проверять capabilities **напрямую backend и через тот же frontend proxy/origin, который использует браузер**. Если значения расходятся, диагностировать routing/proxy/кэш/неверный порт; не менять production defaults на true.
- Добавить fail-fast preflight в исполняемый тестовый контур. При несовпадении печатать только ожидаемые/фактические безопасные capabilities и адреса, прекращать suite до четырёх каскадных UI-таймаутов.
- Проверить frontend AuthContext и DOM: если API возвращает true, а UI скрывает поле, исправлять контракт/обновление состояния. Не подменять server capabilities через JS/localStorage или mocked network.
- Regression-тесты инфраструктуры: старый процесс занимает порт; процесс не запустился; health доступен, но профиль неверный; proxy обращается к другому backend. Каждый случай должен завершаться понятной ошибкой до запуска основной suite.

## 5. G6-WEBAUTHN — пройти lifecycle без ослабления защиты

- Установить доступный Playwright Chromium в тестовом окружении и **фактически запустить** frontend, backend и PostgreSQL. Сборка frontend и unit-тесты не заменяют это действие. Если среда недоступна, фиксировать blocker, продолжая независимую диагностику.
- Согласовать RP ID и точный origin с test frontend, например `localhost` и `http://localhost:5173`, только в явном локальном профиле. Не принимать production и все loopback origins одновременно автоматически.
- Удалить повторную криптографическую верификацию с альтернативным RP ID после ошибки. Неправильный RP ID/origin должен приводить к отказу; параметры доверия приходят из серверной конфигурации, не из недоверенного HTTP-запроса или credential.
- Согласовать options и verification с обязательным user verification согласно ТЗ; использовать виртуальный authenticator с поддержкой UV и соответствующими настройками. Проверить отказ при отсутствии UV, не оставлять `require_user_verification=False` как способ обхода тестов.
- Проверить все четыре исходных сценария: enabled UI; регистрация двух credentials; passwordless login; удаление и невозможность использовать удалённый credential. Обеспечить изоляцию пользователей/аутентификаторов и предсказуемую очистку.
- Проверить network options/verify, сериализацию credential, challenge, CSRF, RP ID/origin и ответ сервера. Если после исправления runtime появится новый сбой, устранить его по доказательствам, а не заканчивать на устранённом первом таймауте.
- Сохранить отрицательные проверки wrong origin, wrong RP ID, missing UV, expired/replayed challenge, чужого/удалённого credential. Не заменять реальную криптографию успешными mock-ответами.
- Trace/screenshot/error-context/backend log сохранять при ошибке. Тест должен быстро показывать отказ API или несовпадение профиля; увеличить timeout можно лишь при доказанной необходимости ожидания, не для скрытого повтора сбоев.

## 6. G6-VERIFY — воспроизводимость и удалённая приёмка

1. Пройти default-off SSO suite и enabled Passkey suite в одном документированном запуске на чистом изолированном стенде, повторить цикл start→test→stop, чтобы подтвердить отсутствие старых процессов. Сохранить команды и результаты обоих прогонов.
2. Каждый Passkey-тест должен работать отдельно; полный набор — без зависимости от порядка и ранее сохранённых credentials. Seed failures не игнорируются.
3. Запустить затронутые backend WebAuthn/security tests, lint/typecheck/build и остальную обязательную регрессию CI. Не удалять/skip/xfail тесты, не добавлять continue-on-error или бесконтрольные retries.
4. Исправления управления процессами включить в CI, а не оставить локальным обходом. Автоматически сохранять диагностику при failed startup/preflight и browser failure.
5. Commit/push выполнять при действующей авторизации владельца. Если авторизации нет, подготовить изменения и запросить её; если сеть недоступна, сообщить конкретный сбой. Не делать force-push и не публиковать релиз. Файл goal не является отдельным разрешением на внешние записи.
6. Получить полный успешный GitHub Actions run **именно отправленного финального SHA**. При новом падении разобрать артефакты и продолжить исправление; предыдущие локальные цифры не заменяют результат CI.
7. Если браузерный прогон или remote CI остаются blocked/not_run, цель не достигнута. Оставить точку продолжения и незакрытые критерии; не писать «готово полностью, осталось владельцу push».
