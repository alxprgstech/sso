## 2. Подтверждённый baseline

Источники — логи, предоставленные владельцем, и ограниченная сверка локального кода. Сначала получить фактический `head_sha` run и сравнить с checkout; не приписывать локальный HEAD чужому запуску.

- [Backend Tests & PostgreSQL Integration](https://github.com/alxprgstech/sso/actions/runs/36064941763/job/107852405918#logs): enabled-шаг собрал 17 тестов, **6 failed, 11 passed**.
- [Playwright E2E Browser Tests](https://github.com/alxprgstech/sso/actions/runs/36064941763/job/107852405883#logs): **5 failed, 3 passed**.

### 2.1. Backend: наблюдения

1. `test_default_features_all_disabled_in_api`: `FEATURE_TOTP_ENABLED=True`, ожидалось `False`.
2. `test_email_verification_default_off_isolation`: endpoint вернул 200 вместо ожидаемого 404.
3. `test_passkey_default_off_isolation_pg`: `FEATURE_PASSKEY_ENABLED=True`, ожидалось `False`.
4. Три Passkey-сценария (`options_and_challenge_persistence`, `multiple_credentials_and_deletion`, `negative_crypto_checks_no_mocks`) падают на входе: 401 вместо 200.

В прочитанном workflow enabled-шаг выставляет все четыре флага и `REQUIRE_VERIFIED_EMAIL=true`, затем запускает файлы, содержащие одновременно default-off и enabled проверки. В Passkey-тестах настройки копируются из окружения с изменением только флага Passkey. Конфликт default-off подтверждён; для 401 дополнительно сохранить тело ответа и состояние пользователя, чтобы доказать влияние неподтверждённого email, а не угадывать его.

### 2.2. Playwright: наблюдения и гипотезы

- Три WebAuthn-сценария не находят `passkey-success` после регистрации. Таймаут локатора — симптом; нужен текст ошибки UI, trace и запросы options/verify.
- Регистрация пользователя проходит до попытки входа, затем не появляется «Личный кабинет».
- Завершающий сценарий закрытия регистрации ожидает «Открыта (open)», но не находит её.
- CI запускает backend со всеми функциями и обязательным подтверждением email, а обычный SSO-сценарий ожидает вход только что зарегистрированного пользователя без подтверждения. Проверить фактический 401 и исправить контракт профиля/сценария.
- В прочитанном enabled backend step нет явных `WEBAUTHN_RP_ID` и `WEBAUTHN_ORIGIN`; Settings использует production-домен, браузер CI — loopback. Это гипотеза причины WebAuthn-ошибки: подтвердить через trace и значения безопасной конфигурации.
- В E2E есть подготовка данных через Python с fallback DSN и `catch`, который лишь печатает ошибку. `sso.spec.ts` использует `beforeAll` и изменяет общую политику регистрации. Проверить повторную инициализацию suite после падения, наследование состояния, доверенные origins/proxy, cookies и реальный frontend→API routing.

## 3. Исправление профилей backend — G5-PROFILES

- Ввести явные, валидируемые тестовые конфигурации: **default-off**, **Passkey enabled**, **email verification required**, **совместимый all-enabled**. Все существенные флаги задаются профилем, а не случайным окружением хоста или локальным `.env`.
- Выбрать согласованную схему: отдельные процессы/jobs для профилей либо fixtures с полной изоляцией настроек приложения. Если используются markers, настроить strict markers и проверять, что обязательные группы действительно собраны, а не дают ноль тестов.
- Отделить проверку настоящих поставляемых defaults от проверки специально сконструированного default-off профиля. Тест defaults создаёт Settings без пользовательского `.env` и влияющих переменных; отдельный HTTP-тест доказывает недоступность функций при false.
- Учитывать `get_settings` cache, dependency overrides и настройки, импортированные сервисами/CLI напрямую. Очищать/восстанавливать состояние в `finally`; overrides HTTP-слоя не должны расходиться с фактическими настройками вызываемого сервиса.
- В Passkey-only сценарии email-политика задаётся явно. В all-enabled + required-email пользователь проходит настоящий подтверждающий flow; запрещено выключать обязательность в середине сценария, чтобы обойти отказ.
- Default-off тесты не запускать под глобальным enabled-контрактом без локальной изоляции. Не удалять их из общего покрытия. Прогнать каждую группу отдельно и вместе в согласованном запуске, подтвердить отсутствие утечек состояния и зависимости от порядка.
- Повторить точную команду/матрицу GitHub, а не только привычное `pytest` с локальными defaults; в отчёте привести безопасную таблицу значений профилей и collected/passed/failed/skipped.

## 4. Исправление браузерных сценариев — G5-E2E

### 4.1. Диагностика и окружение

- Скачать доступные trace/error-context артефакты упавшего run, проверить network, browser console, сообщения WebAuthn и backend logs. Если артефакты недоступны, воспроизвести с `trace: retain-on-failure`, screenshots и логами, не содержащими паролей/токенов.
- Определить один origin каждого тестового стенда. `localhost` и `127.0.0.1` не взаимозаменяемы для WebAuthn/cookies. Согласовать baseURL, frontend/API proxy, RP ID, точный origin, issuer и redirect URI. RP ID не содержит scheme/port, origin содержит фактический порт; production-конфигурацию не ослаблять.
- Проверить реальные названия параметров Settings: в прочитанном workflow встречается `ISSUER`, тогда как проект использует `OIDC_ISSUER`. Исправлять только после сверки путей чтения.
- Ожидание запуска должно завершаться ненулевым кодом при истечении срока; readiness должен проверять требуемые зависимости. Не продолжать тесты после безуспешного цикла ожидания.

### 4.2. Разделение профилей и тестовых данных

- Запускать default-off UI и enabled WebAuthn/email сценарии на соответствующих профилях; использовать отдельные экземпляры/БД либо последовательный перезапуск с изоляцией данных. Один always-enabled сервер не является default-off стендом.
- `prepare_e2e_data.py` и каждый hook получают явный защищённый `TEST_DATABASE_URL` и маркер принадлежности тестовому запуску. Убрать fallback на локальную БД; не обходить guard ради seed/cleanup.
- Ошибка подготовки данных должна останавливать тест с первичной ошибкой. Не глотать исключения через `console.error` с последующим продолжением.
- Каждый тест задаёт собственные предусловия, пользователей и режим регистрации; отдельно запущенный тест и перезапущенный worker должны работать. Сценарий «вернуть closed» не должен зависеть от успешного «открыть open» в другом тесте. Cleanup не маскирует основной сбой.
- В default-off регистрации новый пользователь входит без SMTP. В required-email сценарии он получает письмо через локальный приёмник и подтверждает адрес; нельзя просто ожидать кабинет без подтверждения либо выставлять всем новым пользователям verified в коде приложения.

### 4.3. WebAuthn

- Проверить options, преобразование Base64URL/ArrayBuffer, RP ID/origin, создание credential через CDP Virtual Authenticator и verify response. Ошибка API должна быть видна тесту сразу с безопасным диагностическим сообщением, а не только через десятисекундный timeout.
- Сохранить реальные регистрацию двух ключей, passwordless login, удаление и отказ удалённого credential. Создавать/удалять virtual authenticator в контролируемом lifecycle; не терять credential между шагами одного сценария и не наследовать его между независимыми тестами.
- После исправления положительного пути сохранить отрицательные проверки challenge/origin/RP ID/replay/user verification. Не подменять криптографическую проверку mock-успехом, не отключать user verification или проверки origin.
- Не увеличивать timeout/retries и не ослаблять assertions вместо устранения причины. Ограниченный повторный запуск допустим для проверки воспроизводимости после конкретного исправления, с записью всех результатов.

## 5. CI, отправка и доказательства — G5-CI

1. Зафиксировать baseline SHA и версии Linux/Python/Node/PostgreSQL/Chromium; воспроизвести значимые настройки runner локально или в изолированном Linux-контуре.
2. Исправить backend/E2E, добавить regression-проверки на конфликт профилей, ошибку seed, неверный WebAuthn origin и независимость тестов.
3. Проверить оба упавших набора, затем полный workflow: версии, CD-template, backend, SDK, frontend и Playwright. Не добавлять `continue-on-error`, `skip`, `xfail` или пустую выборку для обязательных проверок.
4. Сохранить least-privilege credentials/permissions, закреплённые Actions и сбор артефактов при failure. Не публиковать релиз и не включать CD. Четыре функции остаются false в поставляемой default-конфигурации.
5. До commit проверить отсутствие секретов, дампов и временных артефактов. Сохранить чужие изменения. Commit/push выполнять при действующей авторизации владельца в текущем чате; если её нет — запросить после подготовки проверяемых исправлений. Сам Markdown goal не подменяет авторизацию внешней записи.
6. После push получить run по **точному отправленному SHA**, дождаться результата всех обязательных jobs. Если снова упало — прочитать первое содержательное сообщение, исправить причину, повторить необходимые проверки и цикл отправки. Не закрывать Goal на этапе «осталось только push».
7. При недоступном GitHub/сети/runner/разрешении продолжать независимые локальные задачи, записать конкретный блокер и минимальное действие владельца. Успех локально не переводит удалённую приёмку в passed.

## 7. Критерии завершения

- [ ] Все шесть backend-падений объяснены и устранены; default-off, Passkey, required-email и all-enabled не зависят от случайного окружения и порядка запуска.
- [ ] Пять E2E-падений устранены по первопричинам; регистрация и WebAuthn lifecycle проходят на живом backend/PostgreSQL, включая отрицательные проверки.
- [ ] Seed/cleanup безопасны, ошибки setup не скрываются; каждый E2E запускается отдельно, весь набор проходит на чистой среде.
- [ ] Сохранены защита тестовой БД, email/MFA/RBAC/CSRF/WebAuthn-инварианты, четыре default-off флага и отключённый CD. Обязательные тесты не исключены ради зелёного результата.
- [ ] **Полный удалённый GitHub Actions CI успешен для финального SHA.** Ссылка, SHA и результаты всех jobs записаны. Если после этого изменён исполняемый код/тесты/workflow, соответствующая новая ревизия снова проверена.
- [ ] Документы отражают реальное покрытие и результаты; нет «выполнено полностью» при failed/blocked/not_run обязательных шагах.

Задача ограничена исправлением этих падений и связанных регрессий. Новый UI-дизайн, дополнительные способы входа, production deployment и повторный бесцельный аудит всего проекта не входят в объём.
