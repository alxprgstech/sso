Сэкономлено в простое: **≈0,25 ядра CPU и ≈17 МиБ RSS постоянно** (≈175 ядро-часов в месяц на

необязательных SDK** (`boto3`, `sentry_sdk`) при старте. После их устранения SSO в простое
практически не потребляет CPU.

## 2. Архитектура и карта потребления

### 2.1. Локальная Compose-конфигурация и EC2

| Компонент | `docker-compose.yml` (локально) | `deploy/ec2/compose.yml` (production) | Учтено в стенде |
|---|---|---|---|
| frontend | контейнер nginx, публикация `127.0.0.1:3000` | **нет контейнера**: статика на системном nginx | нет (в EC2 не работает) |
| edge | frontend-контейнер проксирует `/api`, `/oauth` | системный nginx (`deploy/ec2/nginx.conf`) | контейнер nginx как edge |
| backend | `mem_limit 512m`, `cpus 2`, uvicorn 1 процесс | `mem_limit 512m`, `cpus 2`, uvicorn 1 процесс | да |
| db | `mem_limit 512m`, `cpus 2`, образ postgres:16-alpine | `mem_limit 512m`, `cpus 1`, тот же digest | да (EC2-лимиты) |
| migrate | временный контейнер, `alembic upgrade head` | то же | да, измерялся отдельно |

В production статический frontend отдаёт системный nginx (`worker_processes` не задан → `auto`,
на 2 vCPU это 2 worker-процесса), а backend слушает `127.0.0.1:8000`. В контейнере nginx из
локальной конфигурации worker-процессы тоже создаются автоматически; его RAM/CPU измерялись
отдельно и в «общую RAM backend» не включались.

### 2.2. Постоянные и временные процессы

Постоянно работают: `uvicorn` (1 процесс, 2 потока в простое), `postgres` (~8 процессов:
postmaster + background workers + клиентские backend-процессы по числу соединений), edge nginx
(master + workers), Docker init/tini. Временные: контейнер `migrate` при деплое, healthcheck-пробы
(`wget` каждые 10 с для backend, `pg_isready` каждые 5 с для PostgreSQL), процесс `alembic`/CLI.

Механизмы, способные вызывать рост RAM/CPU:

- Argon2id: `memory_cost=65536` КиБ (64 МиБ) на операцию, `time_cost=3`, `parallelism=4`;
  пул из 2 потоков и очередь до 16 операций (`backend/app/core/security.py`);
- клиентские секреты OIDC хешируются и проверяются тем же Argon2id на каждом `/oauth/token`
  (`backend/app/services/oidc_service.py::get_and_validate_client`);
- `selectin`-загрузка четырёх связей `User` на каждый `SELECT users` (`backend/app/models/user.py`);
- пул SQLAlchemy по умолчанию: `pool_size=5`, `max_overflow=10` (до 15 соединений PostgreSQL);
- фоновая задача обслуживания раз в 60 с (`privacy_service.maintenance_loop`) — ~12 DELETE,
  очистка сессий/кодов/аудита и отправка уведомлений;
- импорт `boto3` (SES) и `sentry_sdk` независимо от выбранного провайдера почты и флага Sentry;
- healthcheck, импортирующий настройки приложения;
- два INFO-лога на каждый HTTP-запрос (диагностика приложения + access log uvicorn).

## 3. Методика измерений

Стенд: изолированный Compose-проект `sso-perf` (`artifacts/performance/bench/compose.yml`),
повторяющий EC2-топологию: PostgreSQL 16 (pinned digest) + backend (pinned `python:3.13-alpine`)
+ edge nginx + локальный SMTP-sink. Лимиты контейнеров — как в `deploy/ec2/compose.yml`.
Тестовые пользователи, пароли, RSA/Fernet-ключи и OIDC-клиенты созданы только для стенда
(151 пользователь, реальные Argon2-хеши, подтверждённые TOTP-секреты).

Нагрузка: собственный closed-loop драйвер на `httpx` с реальными протокольными
последовательностями: парольный вход, PKCE S256, обмен кода, ротация refresh, UserInfo,
второй шаг TOTP, Admin API, регистрация. Каждый виртуальный клиент несёт собственный
`X-Forwarded-For` (edge-прокси переписывает заголовок, как production nginx); лимиты
частоты при этом **не отключались** — каждый IP расходует свою квоту, поэтому для сценариев
с лимитами источник менялся между запросами, как у разных реальных клиентов.

Инструменты: `docker stats`, cgroup v2 (`cpu.stat`, `memory.current/peak/stat`, `pids.current`),
`/proc/<pid>/status`, `smaps_rollup` (PSS), `docker inspect`, `python -X importtime`,
счётчик SQL-запросов через SQLAlchemy `before/after_cursor_execute`, `pgbench` для калибровки
хранилища.

Ограничения достоверности (важно):

- Docker Desktop/WSL2 на Windows: fsync в PostgreSQL измерен как **140 мс** на коммит при
  `synchronous_commit=on` (0,8 мс при `off`), тогда как EBS gp3 даёт ~1–3 мс. Поэтому
  latency/RPS на стенде завышены, а короткие окна шумят (±30–50 %). Для сравнения «до/после»
  использованы два режима: «как есть» и `synchronous_commit=off` (быстрое хранилище,
  приближение к EC2); выводы о RAM/CPU/запросах от режима не зависят.
- Абсолютные значения времени старта включают холодный page cache WSL2; на EC2 старт
  быстрее. Сравнение «до/после» выполнено на одном и том же стенде.
- `docker stats` для PostgreSQL включает page cache; рабочее множество считалось как
  `memory.current − inactive_file`, RSS процессов PostgreSQL не суммировался (общие страницы).
- Нагрузочные окна: 10–12 с на сценарий, повторы A/B в 2 раунда; суммарная нагрузка ~25 мин,
  без overnight/стресс-прогонов.

## 6. Причины найденных проблем

1. **Healthcheck импортировал приложение.** `backend/Dockerfile` (HEALTHCHECK) каждые 10 с
   запускал `python -c`, который импортировал `app.config` → pydantic, pydantic-settings,
   cryptography. Замер: 2,72 с wall / 2,54 с CPU и ~30 МБ транзиентной RSS **на каждую пробу**,
   то есть ~25 % ядра постоянно. Это главная причина «простоя» 24,6 %.
2. **Sentry SDK импортировался всегда.** `backend/app/telemetry.py` импортировал `sentry_sdk`
   и интеграции на уровне модуля, даже при `SENTRY_ENABLED=false`; `app/main.py` вызывал
   `register_routes(app)`, который строил OpenAPI-схему при каждом старте. Цена: ~24–38 МБ RSS
   и ~0,1 с импорта; у 100 % установок с выключенной телеметрией это чистая потеря.
3. **boto3 импортировался всегда.** `backend/app/services/ses_email.py` импортировал
   `boto3`/`botocore`, а `registration_service` и `verification_email` импортируют этот модуль
   при старте. Замер: +36 МБ RSS и ~0,8–3,6 с импорта, хотя SES — лишь один из трёх
   провайдеров почты.
4. **Повторная загрузка пользователя на каждый запрос.** `get_current_session`
   (`backend/app/api/deps.py`) уже выбирает `User` с `FOR UPDATE` и `populate_existing`, а
   `get_current_user` выбирал ту же строку ещё раз. Из-за четырёх `lazy="selectin"` связей
   (`backend/app/models/user.py`: roles, password_credential, totp_credential,
   webauthn_credentials) каждый такой SELECT — это 5 запросов. Итог: 14 запросов на `/me`.
   То же в `backend/app/api/oidc.py::authorize` (24 запроса).
5. **Argon2id по client secret на каждом `/oauth/token`.** `OIDCService.get_and_validate_client`
   вызывает `async_verify_password` для confidential-клиента: 64 МиБ и ~0,2 с CPU на запрос,
   причём очередь общая с парольными операциями (2 потока). Измерено: 2,1 rps при C=5 и
   p95 1,8 с; при C=20 появляются `429 authentication_busy`/рост задержки. Парольные параметры
   при этом менять нельзя.
6. **Коммит на каждый аутентифицированный запрос.** `get_current_session` обновляет
   `last_activity_at` и делает `commit()` — одна WAL-синхронизация на запрос. На медленном
   хранилище это 100+ мс на запрос (видно по `me` C=1: p50 103–126 мс при 14 запросах);
   на EC2 gp3 — единицы миллисекунд. Дополнительно вход по паролю делает ~5 коммитов
   (3 upsert лимитов, аудит, сессия).
7. **Очередь Argon2 при перегрузке.** `PASSWORD_MAX_PENDING=16` при 2 потоках: 20
   одновременных входов дают p95 ≈10 с (запросы ждут, а не отклоняются). RAM при этом
   ограничена (одновременно выполняются только 2 хеша), но latency деградирует.
8. **Фоновое обслуживание.** `maintenance_loop` раз в 60 с выполняет ~12 DELETE и рассылку
   уведомлений; на простое CPU почти не даёт, но требует соединения и коротких транзакций.
9. **Два INFO-лога на запрос.** `diagnostic("http_request")` и access log uvicorn пишут по
   строке JSON на каждый запрос — CPU и I/O, дублирование с access log nginx.
10. **Не заданы параметры PostgreSQL и worker-процессов nginx.** В `deploy/ec2/compose.yml`
    PostgreSQL использует дефолты образа (`shared_buffers=128MB`, `max_connections=100`,
    `work_mem=4MB`); в `deploy/ec2/nginx.conf` `worker_processes` не задан (auto). Для
    512 МиБ/1 vCPU это не оптимально (см. §9).

## 7. Выполненные оптимизации

Все изменения — в backend/Dockerfile и backend/app, без изменения публичных API и протоколов.

1. **Нативный healthcheck без импорта приложения** (`backend/Dockerfile`): BusyBox `wget`
   с заголовком `Host`, вычисляемым из `BASE_URL` (`${BASE_URL#*://}`), таймаут 3 с, тот же
   интервал/start-period/retries. Проверяется тот же `/health/live`; поведение при недоступном
   приложении — non-zero exit → `unhealthy`. Замер пробы: ~0,005–0,01 с CPU вместо 2,54 с.
2. **Ленивый `boto3`/`botocore`** (`backend/app/services/ses_email.py`): SDK импортируется
   внутри `get_ses_client`/`send_ses_email`; `ses_email.boto3` по-прежнему доступен лениво
   (совместимость с тестами и внешними патчами). Ошибки botocore импортируются один раз при
   первом использовании.
3. **Ленивый Sentry** (`backend/app/telemetry.py`): SDK и интеграции импортируются только в
   `initialize_sentry`, когда `SENTRY_ENABLED=true` и DSN задан. Добавлены `sentry_active()`,
   `shutdown_sentry()` и no-op `telemetry_span`; `TelemetryFastAPI.__call__` не копирует
   заголовки, когда телеметрия выключена; `register_routes` больше не строит OpenAPI-схему
   при выключенной телеметрии (`backend/app/main.py`). `verification_email.deliver_message`
   использует no-op span вместо импорта SDK.
4. **Переиспользование уже загруженного пользователя** (`backend/app/api/deps.py`,
   `backend/app/api/oidc.py`): `get_current_session` сохраняет `User`, выбранный `FOR UPDATE`
   в той же транзакции, в `request.state.validated_user`; `get_current_user` и `authorize`

## 8. Отклонённые и нереализованные улучшения

| Предложение | Причина отказа/статус |
|---|---|
| Уменьшить `memory_cost`/`time_cost` Argon2id | **Запрещено**: снижает стойкость к перебору. Оставлено 64 МиБ / 3 / 4. |
| Заменить Argon2id для client secret на HMAC-SHA-256 | Могло бы убрать ~0,2 с CPU с каждого `/oauth/token`, но это изменение политики хранения секретов и требует миграции + отдельного security-review. **Рекомендация**, не внедрено. |
| Уменьшить `PASSWORD_MAX_PENDING` (fail-fast 429) | Меняет поведение под нагрузкой; нужен продуктовый выбор. Сейчас 20 входов дают p95 ~10 с вместо быстрых 429. **Рекомендация** после решения владельца. |
| Не коммитить `last_activity_at` каждый запрос (раз в 30–60 с) | Экономит WAL/fsync, но ослабляет точность 12-часового idle-timeout. **Рекомендация**, требует согласования. |
| `SET LOCAL synchronous_commit=off` для `last_activity_at` | Безопасно по смыслу (потеря отметки лишь ускоряет истечение сессии), но меняет гарантии durability транзакции. **Рекомендация** к отдельной проверке. |
| Отключить access log uvicorn | Убирает одну строку на запрос, но снижает наблюдаемость; access log nginx уже есть. **Рекомендация** при подтверждённой экономии. |
| Несколько uvicorn-воркеров | Увеличивает RAM (каждый процесс ~100+ МБ) и число соединений; для 512 МиБ/1–2 vCPU противопоказано. |
| Уменьшить пул SQLAlchemy (`pool_size`) | При измеренных 6–11 соединениях экономия PG <10 МиБ, риск роста latency. Не внедрено. |
| Native AOT/переход на .NET | См. §10. |
| Полный рефакторинг `selectin`-связей | Высокий риск для auth/assurance-путей; выигрыш меньше, чем даёт переиспользование пользователя. |

## 9. Рекомендуемые ресурсы сервера

Измеренное рабочее множество (production-профиль: system nginx + db + backend):
backend 83–111 МБ (в зависимости от метрики), PostgreSQL 54–79 МБ, nginx 5–25 МБ
(2 worker-процесса), плюс ОС и Docker (ориентир 150–250 МБ для минимального Ubuntu/Debian
с dockerd, sshd и journald). Транзиентные пики: +64 МБ на одну операцию Argon2, +64 МБ на
вторую параллельную; миграция +64 МБ (кратковременно).

| RAM сервера | Вердикт | Комментарий |
|---|---|---|
| **512 МБ** | **Экспериментально, не гарантируется** | ОС+Docker+Docker-сеть ~180–250 МБ, backend ~90–110 МБ, PG ~60–80 МБ, nginx ~20 МБ → 350–460 МБ без запаса; один вход по паролю добавляет 64 МБ, второй — ещё 64 МБ. Нужны swap 512 МБ–1 ГБ, `shared_buffers=64MB`, `max_connections=30`, лимиты контейнеров backend 320–384m / db 256m и запрет одновременных миграций с нагрузкой. Риск OOM при всплеске входов. |
| **1 ГБ** | **Гарантированно устойчиво** | Постоянно ~250–300 МБ, пик с двумя Argon2 ~430–480 МБ, остаётся page cache и запас. Рекомендуемый минимум для production. |
| **2 ГБ** | **Комфортно** | Запас на page cache, резервные копии, обновления и 2–3 параллельных Argon2. |

Важно: в `deploy/ec2/compose.yml` `mem_limit` backend и db по 512m, то есть суммарный лимит
**1 ГБ** — на 512 МБ-хосте контейнерные лимиты не защищают от OOM хоста. Для 512 МБ их нужно
уменьшать согласованно (backend 320–384m, db 256m) либо не использовать такую конфигурацию.

## 10. Оценка перехода на .NET

Это архитектурная оценка, **не прототип**; числа ниже — не измерения .NET-реализации.

- **ASP.NET Core (JIT, .NET 10 LTS).** Минимальный Kestrel-сервис — ~35–50 МБ RSS; с EF Core +
  Npgsql, OpenIddict (OIDC server), Fido2/WebAuthn-библиотекой, Argon2 и JWT-стеком реалистично
  90–160 МБ. Это **не меньше** оптимизированного FastAPI (83–111 МБ), а с большой вероятностью
  больше. Выигрыш по CPU возможен на «питоновских» путях (сериализация, SQLAlchemy, middleware),
  но не на Argon2id, RSA-подписи и PostgreSQL — там работают нативные библиотеки.
- **Native AOT.** Даёт 10–30 МБ RSS и старт <100 мс, но EF Core (компилируемые модели),
  OpenIddict, Fido2/WebAuthn и JSON-полиморфизм требуют source generators и имеют ограниченную
  AOT-совместимость. Полный AOT-стек для SSO с MFA/WebAuthn — исследовательская задача с
  высоким риском регрессий безопасности.
- **Совместимость.** PostgreSQL/Npgsql, OIDC, TOTP, WebAuthn (Fido2NetLib), Argon2
  (Konscious) существуют, но эквивалентность поведения (одноразовые коды, replay-детекция
  refresh, порядок блокировок, assurance-снимки, CSRF/PKCE/nonce, WebAuthn UV/origin) придётся
  доказывать заново.
- **Сложность миграции.** ~6–7 тыс. строк backend, 16 миграций, 100+ тестов, security-инварианты;
  реалистично — месяцы работы и этап параллельной эксплуатации. Для одного инстанса SSO с
  текущей нагрузкой (единицы запросов в секунду) выгода не оправдывает риск.
- **Вывод.** Переходить на .NET сейчас **не стоит**. Приоритет — дальнейшая точечная
  оптимизация FastAPI и вынос тяжёлых операций (Argon2, аудит) в контролируемые границы.
  Пересмотреть при устойчивой нагрузке >100 rps, требовании multi-tenant или появлении
  зрелой AOT-поддержки всего стека.

## 11. Остаточные риски и следующие проверки

1. **Argon2-очередь и client secret.** Рекомендуется отдельное решение владельца:
   (а) перевести client secret на быстрый keyed-hash с миграцией; (б) уменьшить
   `PASSWORD_MAX_PENDING` для fail-fast. До решения под всплеском входов возможны p95
   в секунды и `429 authentication_busy`.
2. **Хранилище.** Локальные latency-замеры ограничены медленным fsync Docker Desktop.
   Нужен короткий прогон на EC2-подобном диске (gp3) для подтверждения p95 и пропускной
   способности; текущие цифры — только для сравнения «до/после» и для CPU/RAM.
3. **PG-параметры.** `shared_buffers=128MB`, `max_connections=100` не проверялись под
   длительной нагрузкой. Для 512 МБ рекомендуется `shared_buffers=64MB`, `max_connections=30`,
   `work_mem=2–4MB`; нужен A/B на реальном объёме данных.
4. **Sentry-путь.** Ленивый импорт проверен unit-тестами, но реальная отправка событий при
   `SENTRY_ENABLED=true` в этой сессии не поднималась (нужен стенд с DSN). Перед production —
   smoke-тест телеметрии.
5. **Долгие прогоны.** Не выполнялись overnight/стабильностные тесты; утечки не обнаружены
   за 30 с после нагрузки, но 24-часовой soak остаётся отдельным этапом.
6. **Nginx/ОС.** `worker_processes auto` и системные лимиты не менялись; для 1 vCPU
   рекомендуется 1 worker и проверка `worker_connections`.
