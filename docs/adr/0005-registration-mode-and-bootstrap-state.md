# ADR 0005: Управление режимом регистрации и атомарное состояние первого запуска

## Контекст

В рамках `GOAL-02-registration-and-setup.md` в ALXPRGS SSO внедряются два ключевых механизма:
1. **Самостоятельная регистрация обычных пользователей** (REG-01..09): серверная политика `registration_mode` (`closed` или `open`), управляемая централизованно, с возможностью переключения администратором через интерфейс и защитой от обхода.
2. **Простой и безопасный первый запуск** (SETUP-01..10): мастер терминальной инициализации, исключающий передачу паролей в аргументах, автоматически закрывающий возможность повторной инициализации и предотвращающий несанкционированное повышение существующих пользователей.

Критически важно исключить состояние гонки (race conditions) при параллельном первом запуске, гарантировать сохранение существующих учётных записей при миграции, а также предотвратить открытие повторного bootstrap при блокировке или удалении администратора.

## Решение

1. **Централизованное хранение в таблице `system_configuration`**:
   - Создаётся отдельная таблица `system_configuration` в PostgreSQL с ограничением `CHECK (id = 1)`, обеспечивающим существование ровно одной записи в системе.
   - Поля:
     - `id: int primary key default 1 check (id = 1)`
     - `bootstrap_completed: bool default false not null`
     - `bootstrap_completed_at: timestamptz nullable`
     - `registration_mode: varchar(32) default 'closed' not null check (registration_mode in ('closed', 'open'))`
     - `updated_at: timestamptz not null`
   - Использование `SELECT ... FOR UPDATE` по строке `id = 1` даёт предельную строгость атомарных транзакций в PostgreSQL как для первого запуска, так и для переключения режима регистрации.

2. **Правила миграции существующих установок (SETUP-06, REG-02)**:
   - При применении миграции Alembic:
     - Если в таблице `users` уже существует хотя бы один пользователь с `is_superuser = true`, создаётся запись `bootstrap_completed = true`, `registration_mode = 'closed'`.
     - Если суперпользователей нет, создаётся запись `bootstrap_completed = false`, `registration_mode = 'closed'`.
   - Таким образом, при обновлении существующей системы регистрация остаётся закрытой, а мастер повторно не активируется.

3. **Инварианты первого запуска (bootstrap)**:
   - До завершения мастера (`bootstrap_completed = false`) публичная регистрация безусловно заблокирована сервером (HTTP 403 Forbidden).
   - Мастер первого запуска выполняется в транзакции:
     1. Блокирует строку `system_configuration` через `SELECT ... FOR UPDATE`.
     2. Проверяет `bootstrap_completed`: если `true`, выводит информационное сообщение и немедленно завершает работу с кодом 0 (идемпотентность).
     3. Проверяет уникальность указанного `username` и `email`: если пользователь с такими данными уже существует, операция отклоняется с ошибкой (запрет неявного повышения обычных аккаунтов).
     4. Создаёт роли `admin` и `user` (если ещё не созданы).
     5. Создаёт пользователя с правами `is_superuser = true`, ролью `admin` и безопасным Argon2id хешем пароля.
     6. Устанавливает выбранный пользователем `registration_mode` (`open` или `closed`).
     7. Устанавливает `bootstrap_completed = true`, `bootstrap_completed_at = now()`.
     8. Фиксирует транзакцию (`commit`).
   - Если транзакция прерывается, наполовину созданные данные откатываются (`rollback`).
   - Удаление или блокировка администратора в будущем не сбрасывает флаг `bootstrap_completed = true`, исключая повторную инициализацию.

4. **Инварианты самостоятельной регистрации (REG-01..09)**:
   - Эндпоинт `POST /api/v1/auth/register` проверяет:
     1. `bootstrap_completed == true` и `registration_mode == 'open'`. При несоблюдении возвращает `403 Forbidden` (`registration_closed`).
     2. Входная Pydantic-схема принимает строго поля `username`, `email`, `password`, `confirm_password`. Все поля ролей, флагов суперпользователя и безопасности запрещены схемой (`extra="forbid"`).
     3. Валидация: длина пароля >= 8 символов, совпадение подтверждения, синтаксис email, допустимые символы логина.
     4. Нормализация идентификаторов: `username = username.strip()`, `email = email.strip().lower()`.
     5. Создание записи пользователя с ролью `user`, `is_active = true`, `is_superuser = false`, `email_verified = false`.
     6. При коллизии уникальности (`username` или `email` уже заняты) возвращается единая ошибка `409 Conflict` (`user_already_exists`) без раскрытия, какое именно поле совпало (защита от перечисления пользователей).
     7. Сессия после регистрации не выдаётся: возвращается приглашение войти.
     8. Ограничение частоты запросов (rate limiting) защищает от исчерпания CPU затратным хешированием Argon2id.

5. **Переключение режима администратором**:
   - Для смены `registration_mode` администратор отправляет запрос с обязательным подтверждением своего текущего пароля (re-authentication).
   - Смена режима логируется в `audit_events` с фиксацией IP, User-Agent и предыдущего/нового значения.
   - Изменение сразу же применяется ко всем инстансам, так как проверяется по данным таблицы PostgreSQL.

## Последствия

- Полная совместимость с существующей схемой данных и пользователями.
- Строгая гарантия атомарности и невозможности повторного захвата роли администратора.
- Безопасное разделение прав между обычными пользователями и администрацией.
