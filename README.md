# ALXPRGS Single Sign-On (SSO)

Закрытая программная система единого входа (Single Sign-On) и централизованной идентификации для экосистемы `alxprgs.tech`.

- **Целевой домен**: `alxprgs.tech`
- **Идентификатор поставщика (Issuer)**: `https://auth.alxprgs.tech`
- **Версия продукта**: `0.2.0` (SemVer, единый источник истины — `VERSION`)
- **Статус**: Готов к локальной эксплуатации и развёртыванию

---

## 1. Быстрый запуск (Быстрый старт)

Для запуска ALXPRGS SSO на рабочей станции требуются только установленный **Docker** с поддержкой **Compose** и штатная командная оболочка (PowerShell на Windows, Bash на Linux/macOS). Установка Python или Node.js на хост не требуется (SETUP-01).

### 1.1. Запуск одной командой

**Windows (PowerShell):**
```powershell
.\start.ps1
```

**Linux / macOS (Bash):**
```bash
chmod +x start.sh
./start.sh
```

### 1.2. Что выполняет мастер запуска

1. **Проверка окружения**: проверяет наличие `docker` в PATH, доступность демона Docker и доступность порта `127.0.0.1:3000` (TEST-SETUP-04).
2. **Безопасная конфигурация**: автоматически генерирует локальный файл `.env` с уникальными криптостойкими ключами (`SESSION_SECRET_KEY`, `TOTP_ENCRYPTION_KEY`, пароль БД) без перезаписи уже существующего файла (SETUP-04).
   Windows-скрипт записывает файл в UTF-8 без BOM. Для контейнеров пароль `POSTGRES_PASSWORD` совпадает с паролем в `DATABASE_URL` и `DATABASE_URL_SYNC`; оба URL указывают на сервис `db`.
3. **Запуск сервисов**: поднимает изолированный контур Docker Compose (база данных PostgreSQL 16, бэкенд FastAPI, фронтенд Nginx + React).
4. **Проверка готовности**: ожидает успешного прохождения liveness healthcheck (`/health/live`) с контролем таймаута (до 60 секунд).
5. **Интерактивный мастер первого администратора (SETUP-03..SETUP-07)** запускается только после успешного старта контейнеров и проверки готовности. Если Compose сообщает, что backend `unhealthy`, скрипт остановится до запросов логина, email и пароля:
   - Запрашивает логин администратора (по умолчанию: `admin`);
   - Запрашивает контактный email (по умолчанию: `admin@alxprgs.tech`);
   - Запрашивает пароль администратора со **скрытым вводом в терминале** (`getpass`) и обязательным подтверждением (минимум 8 символов);
   - Предлагает выбрать режим самостоятельной регистрации обычных пользователей:
     - `[1] closed` (закрытый режим, рекомендуется по умолчанию);
     - `[2] open` (открытый режим со свободной регистрацией).
6. **Готовность**: выводит ссылки на интерфейс и открывает браузер.

Адреса сервисов:
- Пользовательский интерфейс и шлюз: `http://localhost:3000` (привязка строго к `127.0.0.1:3000`, SETUP-08);
- Панель администратора: `http://localhost:3000/admin`;
- База данных PostgreSQL: порт 5432 **не публикуется наружу** для защиты корпоративных данных (SETUP-08).

Если прежний запуск создал некорректный `.env` и остановился **до первого запуска контейнеров**, удалите только этот файл и повторите мастер: он создаст новые секреты. Если PostgreSQL уже запускался с этим файлом, сначала сохраните данные и согласуйте пароль БД и ключи; простая замена `.env` может лишить доступа к существующей базе и сессиям. Содержимое `.env` не отправляйте в чат и не коммитьте.

Если в логах БД есть `Database directory appears to contain a database; Skipping initialization` и `password authentication failed for user "sso_user"`, сохранённый том PostgreSQL использует другой пароль, чем текущий `.env`. До исправления подключения мастер администратора не запустится. Если данные нужны, восстановите прежние реквизиты БД вместо сброса. Для **полного удаления локальных данных приложения** на Windows выполните из PowerShell:

```powershell
.\reset-local.ps1
.\start.ps1
```

`reset-local.ps1` требует вручную ввести `УДАЛИТЬ SSO`. Он остановит контейнеры проекта `sso`, удалит его том `sso_sso_db_data` вместе со всеми пользователями, сессиями и настройками в БД, затем удалит локальный `.env`. Образы Docker и резервные копии вне проекта остаются. Скрипт работает с текущим Docker context, имя которого показывает перед подтверждением. После сброса `start.ps1` создаст новую БД и новые секреты; только при успешном запуске он запросит данные первого администратора. Не запускайте сброс, если данные требуется сохранить.

### 1.3. Повторный запуск и идемпотентность (SETUP-05, SETUP-06)

Повторное выполнение `.\start.ps1` или `./start.sh`:
- Не перезаписывает существующий `.env` и секреты;
- Не сбрасывает базу данных и созданных пользователей;
- Не запрашивает повторный ввод пароля администратора и завершается со статусом 0;
- При наличии существующего обычного пользователя мастер отказывает в автоматическом повышении прав (SETUP-06).

Резервная команда ручного запуска мастера внутри контейнера:
```bash
docker compose exec -it backend python -m app.cli.bootstrap_admin
```

## 2. Архитектура и функциональные возможности

### 2.1. Регистрация и управление режимом (REG-01..REG-09)
- **Открытый режим (`open`)**: на странице входа отображается ссылка на форму регистрации (`RegisterPage.tsx`). После ввода данных создаётся заявка, письмо содержит шестизначный код и одноразовую ссылку. Учётная запись с ролью `user` появляется только после подтверждения email.
- **Закрытый режим (`closed`)**: по умолчанию при первой установке и обновлении существующих инстансов. API блокирует создание пользователей (HTTP 403), интерфейс скрывает ссылку на регистрацию.
- **Управление из панели администратора**: администратор может переключать режим в реальном времени на вкладке «Конфигурация» с обязательным подтверждением текущего пароля администратора (re-auth, REG-02). Изменение немедленно вступает в силу для всех процессов без перезапуска.
- **Безопасность регистрации**: защита от коллизий без раскрытия полей (HTTP 409), строгая запрещающая схема (`extra="forbid"`), межпроцессный rate limiting через аудит PostgreSQL и скользящее окно в памяти, валидация Origin/CSRF.

### 2.2. Сервер аутентификации и OIDC Provider (`backend/`)
- FastAPI + PostgreSQL 16 + SQLAlchemy 2.0 (драйвер `psycopg`);
- Хеширование паролей Argon2id (RFC 9106);
- OpenID Connect Core 1.0 Provider:
  - Discovery (`/.well-known/openid-configuration`), JWKS (`/jwks.json`);
  - Authorization Code Grant с обязательным PKCE S256 (RFC 7636);
  - Выпуск RS256 JWT Access Token (5 мин) и ID Token;
  - Ротация Refresh Token с детектированием Replay (Token Family Replay Detection, SSO-05);
  - Эндпоинт UserInfo (принимает только Bearer Access Token);
  - Отзыв токенов (RFC 7009) и RP-initiated Logout;
- Защита от перечисления пользователей при входе;
- Серверный RBAC с разграничением прав суперпользователя и защитой последнего администратора (USR-08).

### 2.3. Пользовательский веб-интерфейс (`frontend/`)
- React 18, TypeScript, Vite, Tailwind CSS;
- Страница входа с адаптивной поддержкой OIDC-параметра `return_to`;
- Страница самостоятельной регистрации (`RegisterPage.tsx`);
- Личный кабинет: профиль, смена пароля, мониторинг и мгновенный отзыв активных сессий;
- Панель администратора: управление пользователями, регистрация OIDC-клиентов с однократным показом секрета (USR-09), журнал аудита в реальном времени, управление режимом регистрации.

### 2.4. Python SDK `alxprgs-sso` (`packages/python-sdk/`)
- Полная изоляция от внутренних модулей сервера (раздел 3 AGENTS.md);
- Кэширование JWKS с TTL и криптографическая проверка RS256 токенов;
- Интеграция с FastAPI (`SSOFastAPISecurity`, зависимости `get_current_user`, `require_role`);
- Два демонстрационных клиента в `examples/client1` и `examples/client2`, демонстрирующих бесшовный SSO.

## 3. Обязательные инварианты и флаги отложенных возможностей

TOTP, Passkey и Recovery codes отключены по умолчанию. Подтверждение email обязательно при открытой самостоятельной регистрации; отключить его флагом нельзя:

```env
FEATURE_TOTP_ENABLED=false
FEATURE_PASSKEY_ENABLED=false
FEATURE_RECOVERY_CODES_ENABLED=false
FEATURE_EMAIL_VERIFICATION_ENABLED=true
REQUIRE_VERIFIED_EMAIL=false
```

- При выключенных флагах эндпоинты TOTP, Passkey, Recovery codes и Email verification возвращают HTTP 404 (`feature_disabled`);
- Письма не отправляются; тестовый `sent_emails_sink` не пополняется;
- В default-профиле учетные записи администраторов и зарегистрированных пользователей создаются с `email_verified=False`;
- `REQUIRE_VERIFIED_EMAIL=true` дополнительно блокирует вход ранее созданных или созданных администратором пользователей с неподтверждённым адресом. Самостоятельная регистрация всегда подтверждает email до создания пользователя.

### Отправка писем подтверждения

При открытой регистрации нужен работающий почтовый транспорт: `EMAIL_PROVIDER=smtp` по умолчанию с параметрами `SMTP_*`. Для SES API v2 задайте в локальной конфигурации `EMAIL_PROVIDER=ses`, `SES_REGION=us-east-1`, `SES_FROM_EMAIL=sso@alxprgs.tech` и `SES_FROM_NAME=ALXPRGS`; при необходимости измените последние три значения. Пароль и AWS credentials не сохраняйте в репозитории. SES использует стандартную цепочку AWS credentials и IAM role. Оба транспорта отправляют `text/plain`, `text/x-amp-html`, `text/html`; обычные текст и HTML работают независимо от поддержки AMP. Код и ссылка действуют 10 минут. Ссылка погашается только по нажатию пользователя.

`POST /api/v1/auth/register` теперь отвечает HTTP 202 с `challenge_id`, `expires_at`, `request_details` вместо HTTP 201 с `user_id`. Завершите заявку вызовом `/api/v1/auth/register/confirm-code` (`challenge_id`, `code`) либо `/api/v1/auth/register/confirm-link` (`token`). `/api/v1/auth/register/resend` принимает `challenge_id` и выпускает новые код и ссылку; прежние перестают действовать. Клиентам API нужно обновить обработку ответа регистрации. После подтверждения пользователь входит обычным способом.

AWS credentials не записываются в репозиторий или настройки приложения: локально boto3 использует стандартные AWS profile/environment providers, в AWS — IAM role. Для локального Compose стандартные AWS credential variables можно задать в игнорируемом Git файле `.env`; после этого пересоздайте backend-контейнер. Роли требуется `ses:SendEmail` для проверенной identity `alxprgs.tech` в `us-east-1`; custom MAIL FROM `bounce.alxprgs.tech` выбирается настройкой identity в SES. Пока аккаунт в SES sandbox, произвольные получатели недоступны. Успех API означает принятие письма SES, но не подтверждённую доставку. Порядок настройки и диагностики: [эксплуатация](docs/operations.md).

Для локальной проверки TOTP, Passkey и резервных кодов установите в сохранённом `.env` значения `FEATURE_TOTP_ENABLED=true`, `FEATURE_PASSKEY_ENABLED=true`, `FEATURE_RECOVERY_CODES_ENABLED=true`. Скрипты первого запуска создают `WEBAUTHN_RP_ID=localhost` и `WEBAUTHN_ORIGIN=http://localhost:3000`; в ранее созданном `.env` задайте эти два значения вручную. Открывайте интерфейс именно по `http://localhost:3000` (не через `127.0.0.1` или другой порт). После изменения конфигурации пересоздайте backend командой `docker compose up -d --force-recreate backend` и обновите страницу браузера; фактические флаги проверяйте через `/api/v1/auth/capabilities`. Резервные коды доступны после подключения TOTP. Значения по умолчанию остаются `false`; production требует отдельного HTTPS origin и RP ID.

При подключении TOTP кабинет показывает QR-код из серверного `otpauth_url` с названием ALXPRGS SSO и адресом учётной записи. Секрет можно ввести вручную или скопировать кнопкой. QR и секрет показываются только на шаге подключения до подтверждения одноразовым кодом.

## 4. Тестирование и верификация

### 4.1. Автоматизированные тесты pytest

```bash
# Только на выделенном PostgreSQL после установки зафиксированных зависимостей,
# миграций, явной настройки TEST_DATABASE_URL и отдельного создания маркера
# по docs/operations.md; fixture не создаёт маркер за вас:
python -m pytest tests/ -v
```

Тестовый комплект покрывает:
- OIDC Protocol: PKCE S256, Authorization Code, Token, UserInfo, Refresh Token Replay Detection;
- Регистрация и управление режимом (`tests/test_registration.py`, 12 тестов): открытый/закрытый режим, коллизии, запрет повышения прав, rate limiting, изоляция email;
- Мастер первого запуска (`tests/test_bootstrap_admin.py`, 7 тестов): первичная инициализация, идемпотентность, отказ в повышении прав обычного пользователя, валидация TTY;
- Отложенные возможности (`tests/test_mfa_features.py`): изоляция default-off и корректность enabled-профиля;
- Административный API и RBAC (`tests/test_admin_api.py`);
- Python SDK unit (`tests/test_python_sdk.py`, `tests/test_sso_cross_clients.py`); реальный двухклиентский SSO проверяется отдельно в Playwright;
- Негативные сценарии безопасности и гонки (`tests/test_security_and_negative_scenarios.py`).
