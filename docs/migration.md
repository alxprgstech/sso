# Инструкция миграции для комплекта выпуска

Сверка документации: 26.10.2026, продукт 0.3.0. [Реестр и границы](index.md), [статус](status.md). Прежние измерения/PASS относятся к указанным датам и ревизиям.

Комплект содержит пакет backend, отдельный архив `alxprgs-sso-migrations-<версия>.tar.gz` с `alembic.ini` и `alembic/versions`, пакет SDK и собранный frontend. Применяйте только комплект, чьи `release-manifest.json` и `SHA256SUMS.txt` прошли проверку целостности. Для EC2 выбран отдельный [push-main CD](ec2-deployment.md) с private transport/image identity. Его автоматический rollback не восстанавливает БД и допускается только при подтверждённой совместимости схемы.

1. В окне обслуживания сохраните резервную копию PostgreSQL проверенной штатной процедурой и проверьте возможность восстановления на **отдельной** базе. Храните секреты шифрования TOTP и ключи подписи отдельно от архива БД; без прежнего TOTP-ключа существующие записи нельзя расшифровать. Не восстанавливайте поверх рабочей БД для проверки.
2. Сверьте версию и SHA комплекта с утверждённым тегом, прочитайте `RELEASE_NOTES.md` и текущую схему миграций. Установите backend wheel и обновите конфигурацию после проверки различий настроек. Три MFA-флага и `REQUIRE_VERIFIED_EMAIL` остаются выключенными в default-профиле; самостоятельная регистрация всегда требует подтверждения email, `FEATURE_EMAIL_VERIFICATION_ENABLED=false` запрещён. Production требует постоянный RSA key с явным безопасным `JWT_KEY_ID`, случайные session/TOTP secrets, согласованные HTTPS origins и verified SMTP TLS либо SES. Подробнее — [ротация и роли БД](operations.md).
3. Распакуйте архив миграций в каталог, где доступен установленный backend. Для старого volume сначала выполните offline-передачу application objects выделенному `sso_migrator` по [runbook](operations.md#раздельные-роли-бд-и-обновление-существующего-volume). Затем задайте `DATABASE_URL_SYNC` миграционной роли через защищённое окружение и выполните `alembic -c alembic.ini upgrade head`. Runtime использует отдельный `sso_runtime` с DML, без DDL/ownership/superuser. Не вставляйте DSN или секреты в логи и команды, сохраняемые в истории терминала.
4. Проверьте revision через `alembic -c alembic.ini current`, затем запустите приложение и выполните health/readiness, вход, logout и проверку OIDC-клиентов. После этого переключайте трафик согласно выбранной инфраструктуре.
5. При отказе остановите переключение. Перед восстановлением из backup сохраните наблюдаемую ошибку без секретов и проверьте целевой сервер/БД. Откат схемы через `alembic downgrade` без отдельного анализа конкретной миграции не предполагается; восстановление выполняется из проверенной копии в отдельный контур и затем по утверждённому плану возврата.

При переходе с `0004_privacy` на `0010_registration_session` добавляются индексы, security revision, persistent MFA-step/actions, auth_time, scope policy, временные recovery credentials и session binding WebAuthn registration. Старые OAuth grants без достоверного auth_time выводятся из обращения; нужен новый вход. Значение allowed scopes по умолчанию совместимо с прежними `openid profile email`, после обновления владелец каждого клиента ограничивает его фактически необходимым набором. Access Token теперь требует scope и полный профиль claims; SDK обновляется вместе с OP. Старые MFA challenge/session proofs после изменения credentials не действуют, role/block/email/factor events отзывают старые серверные grants. Независимый RP принимает уже выданный access JWT до exp (в production максимум300 секунд); мгновенный глобальный отзыв offline JWT не заявляется.

Пароли при создании/смене:15–128 Unicode символов, offline blocklist, без composition/периодической смены. Уже существующий hash не переписывается; admin reset выдаёт ограниченный временный credential, а не постоянный пароль. Новые recovery codes содержат32 случайных A–Z/0–9 символа и отображаются четырьмя группами по8; это второй фактор после пароля, атомарно одноразовый. Перед включением MFA проверьте существующие enrolments и предусмотренную политику отключения, не меняйте flags посреди пользовательского сценария.

## Unreleased: исправления SEC-01…04

Перед запуском новой реализации выполните `alembic upgrade head` до `0014_registration_browser`. 0011 добавляет nullable Gmail action hash: прежние code/link работают, прежние Gmail action без секрета отвергаются; отправьте новое письмо. 0012 нормализует binary credential IDs в base64url без padding; коллизия или invalid ID останавливают миграцию с общей диагностикой без удаления записей. Сначала исследуйте конфликт в приватной копии, не удаляйте credentials автоматически. 0013 добавляет notification outbox.

SDK теперь отвергает HTTP по умолчанию и запрещает отключение проверки TLS. Локальные клиенты должны явно выбрать `transport_profile="local"`; demo processes — `SSO_TRANSPORT_PROFILE=local`. Серверу для HTTP loopback callbacks требуется `REDIRECT_TRANSPORT_PROFILE=local`; production всё равно требует HTTPS. VERSION этой задачей не изменяется.

Сторонние cookie-клиенты управления сессиями должны получать отдельный read grant через password/configured MFA. Каждый DELETE получает отдельный one-use proof. Все Python dependency installations используют hashed companions и `--require-hashes`, локальные пакеты устанавливаются отдельно с `--no-deps --no-build-isolation`.

### 0014_registration_browser / SSO-SEC-0005
Выполните alembic upgrade head до0014_registration_browser. Добавляется nullable browser_secret_hash в pending_registrations. Существующие незавершённые регистрации больше не подтверждаются/resend без нового browser proof: пользователю нужно повторно начать регистрацию; старые письма не использовать. Существующие аккаунты/сессии не изменяются. Новые письма предлагают Gmail ViewAction в исходный browser; legacy server ConfirmAction без browser cookie отвергается. Downgrade удаляет binding и возвращает риск prehijack; не используйте его как security rollback на открытой регистрации.

### 0015_external_step_up / EXTERNAL-STEPUP-01
Выполните `alembic upgrade head` до `0015_external_step_up` до включения `FEATURE_EXTERNAL_STEP_UP_ENABLED=true`. Миграция добавляет в `oidc_clients` выключенные по умолчанию `step_up_enabled=false`, пустые `step_up_assurance_levels`/`step_up_actions`, `step_up_max_ttl_seconds=300` и таблицу `external_step_up_requests` с уникальными хэшами request/proof и индексами TTL. Существующие OIDC-клиенты, сессии, пользователи и grants не меняются, возможность никому не выдаётся автоматически. После миграции:
1. включите глобальный флаг только в тестовом контуре;
2. для каждого доверенного confidential-клиента через `PATCH /api/v1/admin/clients/{client_id}/step-up` задайте точные assurance/actions/TTL и только затем `step_up_enabled=true`;
3. убедитесь, что TOTP/Passkey flags и фактические credentials соответствуют выбранной политике; при strict без Passkey запросы будут отклонены;
4. обновите SDK до 0.3.0 и сохраняйте `StepUpRequest` (state/nonce/PKCE) на сервере RP.
Downgrade удаляет pending/consumed proof state и возвращает клиентов к выключенной возможности; не выполняйте его при активных административных сценариях. Rollback приложения без downgrade безопасен для OIDC: старый код игнорирует новые таблицы/поля. Pending step-up requests после изменения security revision/сессии инвалидируются.
