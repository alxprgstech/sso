## 4. Обязательные исправления с критериями

### C9-01 / P0 — Безопасность backup/restore и правдивость эксплуатационного теста

**Наблюдение:** [tests/test_ops_backup_restore_totp.py](tests/test_ops_backup_restore_totp.py) использует fallback TEST_DATABASE_URL, подменяет имена БД строковыми replace, удаляет записи до проверки маркера, дважды выполняет `DROP DATABASE IF EXISTS alxprgs_sso_restore_test WITH (FORCE)` и подавляет ошибки cleanup. Docker container/user заданы отдельно от DSN. В CI это может либо повредить существующий стенд, либо обращаться совсем не к тому серверу.

**Исправить:**

- Только явный TEST_DATABASE_URL, без fallback. Разбор DSN библиотекой; рабочая БД/невалидный URL/неподдерживаемая конфигурация отклоняются до любой записи. Не раскрывать пароль в ошибке.
- Отдельные уникальные source/restore БД или эквивалентный доказанно изолированный контур текущего run ID. Не удалять заранее существующую БД с совпадающим именем. Не менять существующие данные общей тестовой БД для удобства сценария.
- До destructive SQL проверять реальную БД, сервер и маркер владения запуском. Cleanup только после успешного создания своим запуском и повторной проверки владения. Несовпадение маркера, чужие соединения или ошибка очистки — видимый отказ, а не `except: pass`. Не использовать FORCE против чужих процессов.
- pg_dump/restore должны обращаться к тому же подтверждённому серверу. Не переходить молча на другой Docker-контейнер, если локального pg_dump/psql нет. SQL-ошибка restore должна давать ненулевой exit code; проверь поведение psql и штатных скриптов.
- Сохранить сценарий реального backup/restore схемы и данных, ролей/сессий/клиентов/TOTP. Проверять восстановленный вход/TOTP через приложение в enabled-профиле, а не только успешный вызов Fernet на заранее зашифрованной строке.

**Доказательство:** unit-тесты отказа до SQL и PG integration с контрольными чужими данными: нет TEST_DATABASE_URL, рабочий DSN, неверный/чужой/отсутствующий маркер, заранее существующая цель, ошибка backup/restore, частичный setup, ошибка cleanup. Чужая БД остаётся неизменной. Положительный тест создаёт и удаляет только собственные ресурсы; восстановленный пользователь проходит реальный проверяемый процесс, неверный ключ не даёт доступ.

### C9-02 / P0 — Безопасные web-сессии примеров и полный callback SDK

**Наблюдение:** [Client 1](examples/client1/app.py) и [Client 2](examples/client2/app.py) сами подписывают содержимое cookie через HMAC с известным APP_SECRET по умолчанию. Подписанные claims принимаются как сессия без серверного TTL/отзыва. `max_age` управляет браузером, но не заменяет проверку сервером. Значения пользователя вставляются в HTML без гарантированного escaping. Это не требуемое серверное хранение web-сессии.

**Исправить:**

- Использовать случайный непрозрачный session ID в защищённой host-only cookie, а flow state/nonce/verifier, пользовательские данные и токены хранить на сервере. Выбрать поддерживаемый механизм, не создавать собственный криптографический формат. Обосновать хранение в ADR; SDK не импортирует backend. Одна in-memory демонстрация допустима лишь при явно документированных ограничениях и соответствии ТЗ; её нельзя объявлять многопроцессной production-сессией.
- Нет известного ключа/секрета по умолчанию, которым можно авторизоваться или подделать сессию. Секреты должны быть предоставлены безопасно либо, для изолированного процесса demo, создаваться при запуске с честно описанным временем жизни. Синтетические credentials E2E передавать только явным тестовым профилем.
- Серверный абсолютный/idle TTL, отзыв, ротация идентификатора после входа, CSRF для изменяющих состояние операций, Secure в HTTPS/production; localhost HTTP допускается только явно.
- State/nonce/verifier привязаны к инициировавшему браузеру, имеют TTL и погашаются одноразово. Callback завершает настоящий code exchange, проверяет ID token/nonce и access token до создания сессии. Cookie не должна нести bearer/refresh токены или доверенные пользовательские роли. HTML escaping обязателен.
- Проверить `SSOClient.verify_id_token`: сейчас при HTTP server_url без explicit issuer выбирается `None`; проверка точного issuer не должна зависеть от схемы транспорта. Проверить `handle_web_callback`: отсутствие ID token не должно позволять пропустить обязательную OIDC/nonce проверку.
- Проверить `/oauth/logout`: в текущем коде `post_logout_redirect_uri` принимается напрямую, `id_token_hint` не используется. Исключить произвольный redirect, связать возврат с валидированным клиентом/зарегистрированным URI и согласовать SDK helper. Локальный logout и глобальные ограничения объяснить точно.

**Доказательство:** неизвестная/подделанная/истёкшая/отозванная cookie → отказ; чужой браузер, неверные state/nonce/issuer, отсутствующий ID token, повтор callback → отказ; успешный вход создаёт серверную сессию, logout отзывает её. Негативные redirect/HTML cases и restart/multi-process поведение согласно выбранному контракту. Тестировать установленный SDK wheel в чистой среде.

### C9-03 / P1 — Настоящий browser E2E двух клиентов

**Наблюдение:** [multi_client_sso.spec.ts](frontend/e2e/multi_client_sso.spec.ts) запускает два `http.createServer`, всегда отвечающих «Callback OK». Тест подтверждает только выдачу code и redirect. В нём нет реальных FastAPI-клиентов, SDK, token exchange, проверки nonce и клиентской сессии. Название теста logout обещает больше, чем проверяется.

**Исправить:** вместо заглушек запускать существующие Client 1/2 как отдельные процессы, использующие установленный из wheel SDK. Связать issuer, frontend/backend origins, client IDs, redirect/logout URI и секреты с изолированным test setup. Fixture отвечает за readiness, раннее сообщение ошибки и cleanup только своих процессов. Не менять серверные capabilities через mock.

**Доказательство в браузере:**

1. Переход из Client 1 → SSO login → callback → реальная защищённая страница и серверная клиентская сессия.
2. Переход во второй настоящий клиент без повторного пароля → успешный callback и независимая сессия второго клиента.
3. Отказы state/nonce/PKCE/redirect, повтор callback и перенос flow в другой browser context. Отсутствие token exchange должно приводить к провалу E2E, а не оставаться незамеченным.
4. Локальный logout действительно закрывает локальный доступ; SSO logout блокирует новую SSO-авторизацию. Существующая сессия второго клиента ведёт себя ровно по документированному контракту, а не обязательно исчезает автоматически.

Новый набор обязателен в CI и release-проверках. Исторические 4/4 тестов заглушек не засчитываются этому критерию.

## 5. Экономный рабочий цикл и доказательства

- На каждую находку: конкретное воспроизведение → regression test с ожидаемым отказом → минимальное исправление → положительные/отрицательные проверки → запись результата. Не переписывать тест под неправильное поведение. Подтверждённую неточность самого задания можно документированно опровергнуть проверкой полного пути.
- Unit safety tests выполнять до опасной integration. Компоненты проверять по мере изменения; общую приёмку — после стабилизации. Не повторять неизменные сборки и долгие soak при каждой правке текста.
- До длительного прогона проверить readiness/короткий smoke. Первый новый сбой диагностировать до повторения группы. Сохранять run ID, seed, версии, длительность чистой нагрузки, PID/владение socket, baseline/final PG, planned/executed browser checks, ошибки и cleanup. Не дописывать прошлые измерения задним числом.
- При блокере записывать наблюдаемую ошибку без секретов и минимальное необходимое действие. Продолжать независимые этапы. Не ждать пользователя там, где решение обратимо и входит в задачу.
- Перед остановкой обновить plan/status/worklog, список изменённых файлов, точную команду продолжения и оставшиеся проверки. Исчерпание ресурсов/лимита сеанса не означает достижения цели.
