## 3. Детализация исправлений и расследований

### 3.1. Дефект G7-START: Аварийное падение Vite preview в CI run 36084939672
- **Симптом**: В GitHub Actions job `playwright-e2e` запуск `manage_test_server.py start-frontend` завершался ошибкой:
  `[START-ERROR] Фронтенд (PID ...) аварийно завершился до готовности http://127.0.0.1:5173`.
  Файл `/tmp/frontend.log` не попадал в артефакты; диагностика отсутствовала.
- **Анализ логов**: В архиве `logs_97718245499.zip` в шагах `playwright-e2e` обнаружено:
  выполнялись `npm ci` и `npx playwright install`, после чего сразу вызывался `start-frontend`. Команда `npm run build` не выполнялась.
- **Воспроизведение**: На чистом checkout при отсутствии папки `frontend/dist` запуск `vite preview` немедленно завершается с кодом 1:
  `Error: The directory "dist" does not exist. Did you build your project?`
- **Примененные исправления**:
  1. В `.github/workflows/ci.yml` добавлен явный шаг сборки:
     ```yaml
     - name: Build frontend
       run: npm run build
       working-directory: frontend
     ```
  2. В `scripts/manage_test_server.py` добавлена preflight-проверка наличия `dist/index.html` перед запуском `vite preview`, а также вывод кода возврата процесса и последних строк лога (`tail`) при аварийном завершении или таймауте.
  3. В `scripts/run_e2e_suite.py` добавлен preflight-контроль и автоматическая сборка фронтенда при ее отсутствии.
  4. В `.github/workflows/ci.yml` обновлен шаг загрузки артефактов при падении: добавлены `/tmp/frontend.log` и `/tmp/backend*.log`.
  5. В `tests/test_server_lifecycle.py` добавлены 4 регрессионных теста:
     - `test_frontend_missing_build_fail_fast`: отказ с понятной ошибкой при отсутствии сборки;
     - `test_frontend_port_already_in_use_fail_fast`: обнаружение занятого порта;
     - `test_frontend_early_crash_diagnostic_log`: вывод кода возврата и лога упавшего процесса;
     - `test_real_frontend_lifecycle_and_port_release`: проверка реального запуска, ответа по HTTP и корректного останова.

### 3.2. Расследование и устранение дефекта замера памяти (G7-SOAK)
- **Симптом в первоначальном отчете**: Зафиксирован подозрительно низкий RSS бэкенда на Windows (~4.5 МБ), что не соответствует реальному footprint FastAPI / uvicorn / SQLAlchemy.
- **Первопричина**: В Windows-окружении запуск через `.venv\Scripts\python.exe -c "..."` порождает два процесса:
  1. Исполняемый stub-launcher `.venv\Scripts\python.exe` (родительский процесс с PID, возвращаемым `proc.pid`), занимающий в памяти ~4.5 МБ Working Set и не выполняющий полезной нагрузки.
  2. Дочерний процесс реального интерпретатора Python (`base_prefix\python.exe`), который загружает runtime uvicorn/FastAPI, выделяет буферы и держит слушающий TCP-сокет на порту 8000. Его реальный Working Set составляет ~92–99 МБ.
  Скрипт `manage_test_server.py` записывал в `pidfile` PID stub-launcher процесса (`proc.pid`), что приводило к сбору телеметрии не с того процесса.
- **Устранение**:
  1. В `scripts/manage_test_server.py` и `scripts/run_overnight_stability.py` реализована функция `get_pid_listening_on_port(port)`, определяющая точный PID процесса, владеющего слушающим TCP-сокетом (`netstat -ano -p tcp` на Windows, `lsof` / `ss` на Linux).
  2. В `start_server` и `start_frontend` после подтверждения ответа по HTTP PID-файл перезаписывается PID фактического слушающего worker-процесса.
  3. В `stop_server` процесс завершается по обоим PID (launcher и listening worker), с гарантированной проверкой освобождения сокета порта.
  4. В `run_soak_stage` добавлена валидация реалистичности памяти: любой замер RSS бэкенда `<= 10.0 МБ` трактуется как ошибка измерения и приводит к отказу этапа (`failure_reasons`).

### 3.4. Исправление объема проверок конкурентности (G7-RACE)
- **Выявленное несоответствие**: В выражении `iterations = max(2, attempts // 5)` при `--race-attempts 10` запускалось только 2 итерации набора вместо требуемых 10 попыток на каждый сценарий.
- **Исправление**: Семантика параметра изменена на прямое соответствие: `iterations = attempts`. При `--race-attempts 10` выполняется 10 полных итераций тестового набора `tests/integration/test_concurrency_pg.py`.
- **Фактический результат прогона (`campaign_race_10att`)**:
  - `auth_code_race`: **10 из 10 попыток успешно** (в каждой попытке ровно 1 обмен из 5 параллельных запросов успешен, 4 отклонены с `invalid_grant`, зафиксирован аудит replay).
  - `recovery_code_burn`: **10 из 10 попыток успешно** (в каждой попытке ровно 1 успешное сгорание, второй запрос отклонен 401).
  - `refresh_replay_race`: **10 из 10 попыток успешно** (обнаружение повторного использования токена, отзыв сессии, аудит `refresh_token_replay_detected`).
  - `concurrent_registration`: **10 из 10 попыток успешно** (ровно 1 создание пользователя, конкурентный запрос получает 409 Conflict).
  - `distributed_rate_limiting`: **10 из 10 попыток успешно** (блокировка 6-го запроса с одного IP с кодом 429).
  - Всего проверок матрицы: **50 из 50 пройдены**.
- **Проверка конечного состояния PostgreSQL**:
  - Проверено отсутствие зависших блокировок (`pg_locks WHERE NOT granted` = 0).
  - Зафиксировано наличие 6 пользователей и 6 аудит-событий после завершения тестов.
  - Таблица `system_configuration` сохранила корректную запись с `id=1`.

## 4. Ограничения стенда и оговорки безопасности

1. **Длительность прогона**: 20-минутный soak-тест (`campaign_soak_20m_corrected`) подтверждает стабильность сервиса под умеренной нагрузкой и отсутствие резких утечек Working Set. 2. **Изоляция окружения**: Тестирование проводилось на локальном стенде Windows/PostgreSQL Docker.
3. **Статус удаленного CI**: Доступ к сетевому пушу в репозиторий GitHub с локального рабочего места ограничен сетевой средой; статус удаленного CI зафиксирован как заблокированный до ручного пуша владельцем. Все изменения локально валидированы и соответствуют полному составу проверок CI.
4. **Инварианты безопасности**: Никакие механизмы защиты (TLS, WebAuthn User Verification, RP ID, CSRF, RBAC, одноразовость) не отключались и не ослаблялись ради прохождения тестов.
