# Техническое задание на систему единого входа ALXPRGS SSO

- **Обозначение документа**: ЕСПД.ГОСТ 19.201-78.ТЗ-01
- **Проект**: ALXPRGS SSO (Система единой аутентификации и авторизации)
- **Версия**: 1.0.0
- **Дата утверждения**: 24.09.2026
- **Статус**: Действующий

---

## 1. Введение

Настоящее техническое задание распространяется на разработку и внедрение закрытой программной системы единого входа (Single Sign-On, SSO) для инфраструктурного контура `alxprgs.tech` с целевым адресом службы идентификации `https://auth.alxprgs.tech`.

Система предназначена для централизованной аутентификации пользователей, разграничения прав доступа на основе ролевой модели (RBAC), предоставления доверенным информационным системам протокольного взаимодействия по стандартам OAuth 2.0 / OpenID Connect Core 1.0, а также предоставления программной библиотеки (SDK) для интеграции сервисов на языке Python.

---

## 2. Основание для разработки

Разработка ведется на основании плана развития инфраструктуры цифровых сервисов ALXPRGS и требований технического задания `GOAL.md` (версия 1.2 от 24.09.2026), а также единого регламента разработки `AGENTS.md`.

## 3. Назначение системы

### 3.1. Функциональное назначение
Система ALXPRGS SSO обеспечивает:
1. Централизованную безопасную аутентификацию пользователей по паролю с алгоритмом хеширования Argon2id (RFC 9106);
2. Поддержку протокола OpenID Connect (OIDC) с обязательным использованием потока Authorization Code Flow и расширения PKCE S256 (RFC 7636);
3. Бесшовный сквозной единый вход (SSO) для внешних веб-приложений и API сервисов без повторного ввода учетных данных при наличии активной сессии;
4. Защиту от повторного использования кодов авторизации и ротацию refresh-токенов с обнаружением атак воспроизведения (Token Family Replay Detection);
5. Предоставление пользовательского веб-интерфейса самообслуживания (личный кабинет, смена пароля, отзыв сессий);
6. Предоставление веб-интерфейса администрирования (управление учетными записями, блокировка пользователей, регистрация OIDC-клиентов с однократным показом секрета, журнал событий аудита);
7. Реализацию механизмов многофакторной аутентификации (TOTP, WebAuthn Passkey, Recovery codes) и подтверждения email с гарантированным отключением по умолчанию на уровне сервера.

### 3.2. Эксплуатационное назначение
Система предназначена для развертывания в изолированной среде с использованием контейнеризации Docker / Docker Compose и реляционной СУБД PostgreSQL 16.

## 4. Требования к системе

### 4.1. Требования к функциональным характеристикам

#### 4.1.1. Аутентификация и сессии
- Хранение паролей исключительно в виде хешей Argon2id с индивидуальной солью (параметры RFC 9106: time_cost=3, memory_cost=64MB, parallelism=4);
- Серверное хранение сессий в PostgreSQL с поддержкой криптографически стойких идентификаторов сессий (32 байта энтропии);
- Передача идентификатора сессии через host-only cookies с флагами `HttpOnly`, `SameSite=Lax`, `Secure` (в production);
- Защита всех мутирующих запросов от CSRF с использованием сессионных токенов и заголовка `X-CSRF-Token`.

#### 4.1.2. Протокол OpenID Connect и OAuth 2.0
- Эндпоинты Discovery (`/.well-known/openid-configuration`) и JWKS (`/jwks.json`);
- Поток `response_type=code` со строгой валидацией `code_challenge_method=S256`;
- Точное соответствие `redirect_uri` зарегистрированным адресам клиента (запрет wildcards, относительных путей и поддоменов);
- Одноразовые authorization codes со сроком жизни не более 60 секунд;
- Выпуск RS256 JWT токенов (Access Token — 5 минут, ID Token — 5 минут) с проверкой `iss`, `aud`, `exp`, `nbf`;
- Эндпоинт `/oauth/userinfo` принимает исключительно Bearer Access Token и строго отклоняет ID Token;
- Эндпоинт отзыва токенов RFC 7009 (`/oauth/revoke`);
- Механизм RP-initiated Logout (`/oauth/logout`) с валидацией redirect-адреса.

#### 4.1.3. Отложенные возможности (Feature Flags)
- Полная программная реализация четырех механизмов: TOTP (RFC 6238), WebAuthn Passkeys (W3C Level 3), резервные коды восстановления, верификация email;
- Обязательное значение флагов `false` по умолчанию:
  - `FEATURE_TOTP_ENABLED=false`
  - `FEATURE_PASSKEY_ENABLED=false`
  - `FEATURE_RECOVERY_CODES_ENABLED=false`
  - `FEATURE_EMAIL_VERIFICATION_ENABLED=false`
  - `REQUIRE_VERIFIED_EMAIL=false`
- При значении `false` соответствующие эндпоинты возвращают HTTP 404 (`feature_disabled`); фоновые рассылки писем не производятся.

#### 4.1.4. Разграничение прав доступа (RBAC)
- Серверная проверка прав администратора (`is_superuser` или роль `admin`);
- Защита последнего администратора от деактивации или снятия административных прав (USR-08);
- Разовый показ секрета конфиденциального клиента при создании или ротации (USR-09).

### 4.2. Требования к надежности
- Атомарность операций погашения одноразовых секретов в рамках транзакций PostgreSQL с блокировкой строк (`FOR UPDATE`);
- Сохранение журнала аудита событий безопасности в персистентном хранилище;
- Корректная обработка сетевых сбоев и ошибок аутентификации со структурированными JSON-ответами.
