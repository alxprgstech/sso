## Контекст

Реальная отправка была сосредоточена в `EmailVerificationService`: текстовое SMTP-письмо через `smtplib`, без общего интерфейса и без других видов уведомлений. ADR-0004 описывал `EmailSender`, которого в коде нет. Проекту нужен SES API v2 с IAM role, не меняющий SMTP по умолчанию и default-off подтверждения email.

## Решение

`Settings.EMAIL_PROVIDER` допускает `smtp` (default) и `ses`; неизвестное значение отвергается при чтении настроек. `EmailVerificationService.send_verification` создаёт токен и письмо, затем вызывает существующий SMTP-код либо узкий `services/ses_email.py`. Отдельный универсальный интерфейс и очередь не вводятся, поскольку других отправителей нет. SES-клиент переиспользуется по региону, boto3 получает credentials стандартной цепочкой, без параметров ключей приложения. SDK выполняет retry; приложение устанавливает только connect/read timeout по 5 секунд. `SendEmail` получает обе UTF-8 версии письма; IAM role должна разрешать `ses:SendEmail` на доменную identity.

API запроса подтверждения остаётся нейтральным даже при сбое доставки, чтобы не раскрывать существование учётной записи. Сбой SES не переключает отправку на SMTP: это скрыло бы неверную конфигурацию и изменило бы выбранный транспорт. Причина фиксируется ограниченным кодом в `email_delivery_failed`; успешно принятый SES Message ID логируется без адресов и содержимого. Полученный ID не подтверждает доставку. In-memory сборщик с сырым токеном доступен только в явном `ENVIRONMENT=testing`.

## Альтернативы и пределы

Полный `EmailSender`/фабрика транспорта отложены до появления нескольких видов писем. SES SMTP credentials отклонены: они требуют отдельного секрета и не используют IAM role так же, как API. Собственный retry отклонён в пользу политики SDK. SES custom MAIL FROM `bounce.alxprgs.tech` настраивается для identity в AWS; приложение не устанавливает подменный `Return-Path`. Приём bounce/complaint событий требует отдельного решения. CI не отправляет реальные письма.
