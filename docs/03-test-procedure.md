## 1. Объект и цель испытаний

### 1.1. Объект испытаний
Объектом испытаний является программный комплекс ALXPRGS Single Sign-On, включающий:
1. Сервер аутентификации и идентификации на базе FastAPI (пакет `alxprgs-sso-backend`);
2. Пользовательский и административный веб-интерфейс на базе React 18 + TypeScript (`frontend`);
3. Библиотеку интеграции Python SDK `alxprgs-sso` (`packages/python-sdk`);
4. Демонстрационные клиенты единого входа (`examples/client1`, `examples/client2`).

### 1.2. Цель испытаний
Подтверждение [действующего ТЗ](01-technical-specification.md), уточнений владельца и [AGENTS.md](../AGENTS.md). Прежние задания удалены; критерии и результаты сохраняются в [приёмке](acceptance.md).

## 2. Условия проведения испытаний

- Операционная система: Linux/Windows согласно workflows; контейнерные основы закреплены digest;
- Среда исполнения Python: Python 3.12 в CI, Python 3.13.16 в backend image; отдельная среда с зафиксированными зависимостями;
- СУБД: PostgreSQL 16;
- Среда исполнения Node.js: Node.js 24, установка frontend через npm ci;
- Автоматизированный фреймворк тестирования: `pytest` версии >= 8.3 с плагинами `pytest-asyncio`.

## 3. Состав и порядок проведения проверок

| № проверки | Направление | Методика проверки | Ожидаемый результат |
| --- | --- | --- | --- |
| ПР-01 | Аутентификация | Тестирование Argon2id хеширования и сверки паролей | Успешная проверка валидного пароля, отклонение невалидного за константное время |
| ПР-02 | Сессии и CSRF | Проверка выдачи host-only cookies и валидации заголовка `X-CSRF-Token` | Запросы без CSRF отклоняются с 403 Forbidden |
| ПР-03 | OIDC Discovery & JWKS | `GET /.well-known/openid-configuration` и `GET /.well-known/jwks.json` | Отдача RFC-валидного OIDC discovery документа и открытых RSA ключей |
| ПР-04 | Валидация PKCE S256 | Сверка тестовых векторов RFC 7636 Appendix B | Корректный verifier проходит; поддельный verifier отклоняется с 400 invalid_grant |
| ПР-05 | Redirect URI | Точное сопоставление `redirect_uri` без использования wildcards | Отклонение любых сторонних доменов и подпутей с ошибкой 400 |
| ПР-06 | Защита от Replay кодов | Попытка повторного использования Authorization Code | Первый обмен успешен; повторный обмен отклоняется с фиксацией в аудите |
| ПР-07 | Ротация Refresh Token | Обмен токена обновления с проверкой Replay | Выдача новой пары; повторное использование старого токена аннулирует всю семью |
| ПР-08 | UserInfo инвариант | Запрос к `/oauth/userinfo` с ID Token вместо Access Token | Строгое отклонение с кодом 401 invalid_token |
| ПР-09 | Отложенные возможности | Проверка TOTP, Passkey, Recovery и обязательного email при default-конфигурации | Три MFA API отдают HTTP 404; email доступен, пользователь не создаётся до подтверждения |
| ПР-10 | RBAC и последний админ | Попытка деактивации единственного администратора | Блокировка операции с возвратом ошибки 403 forbidden с сообщением о защите последнего администратора |
| ПР-11 | Разовый показ секрета | Генерация клиента и ротация секрета | Открытый секрет передается ровно один раз в ответе; в БД хранится только хеш |
| ПР-12 | Python SDK | Сборка wheel/sdist, валидация токенов по JWKS, хелпер PKCE | 100% прохождение тестов SDK без импорта внутренних модулей сервера |
| ПР-13 | Сквозной SSO | Авторизация в Сервисе 1 обеспечивает бесшовный вход в Сервис 2 | Вход в Сервис 2 происходит мгновенно без повторного ввода пароля |
| ПР-14 | Эксплуатационный контур | Запуск Compose, проверка backup/restore БД, ротация ключей | Корректный дамп БД с расчетом SHA-256, восстановление на отдельной БД с `--confirm` и свежим deletion journal |
| ПР-15 | Саморегистрация пользователей (GOAL-02) | Проверка `POST /api/v1/auth/register`: open/closed режимы, валидация полей, коллизии без утечки, rate limiting, Argon2id, запрет выдачи прав | При closed — 403; при open — 202 с challenge_id без User; после подтверждения email — 200 и пользователь с ролью `user`; коллизии — 409 без утечки поля; админские поля отклоняются схемой (422) |
| ПР-16 | Bootstrap администратора и режим системы (GOAL-02) | Интерактивный/неинтерактивный bootstrap, атомарная фиксация `is_bootstrapped`, отказ в повышении пользователя, смена режима с re-auth | Единственный админ, запрет повторного bootstrap (exit 0), отказ повышения (exit 1), смена режима администратором с проверкой пароля |
| ПР-17 | Скрипты первого запуска (GOAL-02) | Запуск `start.ps1` (PowerShell) и `start.sh` (Bash) при отсутствии Docker daemon | Корректный перехват ошибки, понятное сообщение пользователю, завершение с exit code 1 |

## 4. Критерии приемки

Испытания считаются успешно пройденными, если:
1. Все обязательные проверки выбранной ревизии успешны; разрешённый пропуск внешнего email-job в обычном CI не подтверждает доставку;
2. Отсутствуют ошибки сборки фронтенда (`npm run build`) и линтинга/проверки типов (`npm run typecheck`);
3. [acceptance.md](acceptance.md) фиксирует SHA, профиль, команды, результаты и блокеры; прежний PASS не переносится на новый SHA.

## 5. Конфиденциальность и удаление (PRIV-01..09)

Обязательны PostgreSQL privacy tests и backup/restore; frontend unit/component и privacy браузерные сценарии отдельно в default-off/enabled. Enabled проверяет настоящий виртуальный WebAuthn с UV, точным localhost origin/RP и криптографической верификацией. Запускайте privacy.spec.ts с явными TEST_DATABASE_URL/PYTHON_BIN/PLAYWRIGHT_BASE_URL; для enabled дополнительно PRIVACY_ENABLED_PROFILE=1 и соответствующий сервер. Обычные E2E явно подтверждают документы через UI; прямой API не обходит согласие. Фактические команды, результаты и непроверенные внешние условия — [acceptance.md](acceptance.md); детали политики — [privacy.md](privacy.md).


## Web-тема и регрессии раскладки

`cd frontend` → `npx playwright test e2e/appearance.spec.ts`: Browser-hosted UI unit mock-контракты, system/manual/reload/storage/tabs/keyboard/pre-React, contrast ≥4.5 для проверенных текстовых пар и ≥3 для focus/control borders, mouse/labels/password desktop/mobile, fixed cookies reserve/clipping, consent actions, last-admin alert, QR и dialogs. Это не проверка аутентификации. Тот же suite можно направить PLAYWRIGHT_BASE_URL на build с enforced CSP; violations должны отсутствовать. Настоящий `privacy.spec.ts` отдельно использует маркированную PostgreSQL, PYTHON_BIN и PRIVACY_ENABLED_PROFILE=0/1; enabled требует настоящего виртуального WebAuthn с UV. CI и scripts/run_e2e_suite.py включают оба вида проверки. Demo rendering/assets/CSRF unit: `pytest tests/test_demo_theme.py tests/test_demo_sessions.py`; реальный SSO остаётся multi_client_sso.spec.ts.
